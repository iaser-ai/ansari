# Design Document: Non-streaming WhatsApp Answer Endpoint

**Date**: 2026-11-22
**Spec**: 360-whatsapp-non-streaming-answer-endpoint
**Status**: Phase 1 Complete

## Executive Summary

This document summarizes the research findings from Phase 1 and provides design recommendations for implementing a non-streaming answer endpoint for WhatsApp. The endpoint will return a complete answer in one JSON response, with the LLM returning WhatsApp-formatted text directly.

## Research Summary

### 1. WhatsApp Message Components

**Key Findings:**
- WhatsApp supports limited markdown: `*bold*`, `_italic_`, `~strikethrough~`, `` `monospace` ``
- No support for headings, tables, or complex formatting
- 4096 character limit per message
- URLs are auto-linked
- Arabic text requires RTL support

**Components to Handle:**
1. **Text content**: Convert markdown to WhatsApp format
2. **Citations**: Format as inline text with source attribution
3. **Quran/Hadith references**: Format with Arabic + English + reference
4. **Tool call results**: Convert structured data to readable text
5. **Code blocks**: Use monospace or split
6. **Lists**: Convert to WhatsApp bullet/number format
7. **Links**: Auto-linked by WhatsApp

**Recommendation**: Move existing WhatsApp formatter from `apps/whatsapp` to `apps/api` as a shared utility.

### 2. LLM Structured Output

**Key Findings:**
- Gemini supports JSON Schema with `responseMimeType: 'application/json'`
- Function calling is also supported
- Prompt engineering alone is less reliable
- Hybrid approach (JSON Schema + prompt engineering) is best

**Recommendation**: Use **Hybrid Approach (Method 4)**
- JSON Schema for structure
- Prompt engineering for formatting rules
- Type-safe response
- Easy to modify and maintain

**Example Schema:**
```json
{
  "type": "object",
  "properties": {
    "messages": {
      "type": "array",
      "items": { "type": "string" },
      "description": "Array of WhatsApp-formatted messages, each ≤4096 chars"
    }
  },
  "required": ["messages"]
}
```

### 3. Smart Text Splitting

**Key Findings:**
- Multiple libraries available: `llm-chunk`, LangChain's `RecursiveCharacterTextSplitter`, `llm-splitter`
- Custom implementation is also viable
- Need to handle edge cases: long paragraphs, code blocks, lists, Arabic text

**Recommendation**: Use **Custom Hybrid Approach (Option 5)**
- No new dependencies
- Full control over splitting logic
- Handles edge cases well
- Easy to add continuation markers

**Algorithm:**
1. Try paragraphs first (split by `\n\n`)
2. If paragraph too long, split by sentences (split by `. `)
3. If sentence too long, split by words (split by ` `)
4. Add continuation markers (e.g., " (1/3)")

### 4. Thread Lifecycle

**Key Findings:**
- Currently managed in WhatsApp layer
- Need to move to API layer
- Thread expiry is user-configurable (0-24 hours, default 3 hours)
- Race conditions need to be handled

**Recommendation**: Move thread lifecycle to API layer
- Thread identified by user ID + source
- Thread expiry checked at start of each request
- Database transaction with row-level locking for race conditions
- Cleanup old threads when creating new ones

**New Endpoint**: `POST /api/v2/chat/complete`

**Request:**
```json
{
  "message": "What does the Quran say about patience?",
  "expiryHours": 3
}
```

**Response:**
```json
{
  "messages": [
    "*Quran 2:153* (Al-Baqarah)\n\"O you who have believed, seek help through patience and prayer...\"",
    "The Quran emphasizes patience as a means of divine support."
  ]
}
```

## Design Recommendations

### 1. API Endpoint

**Path**: `POST /api/v2/chat/complete`

**Authentication**: JWT from Authorization header

**Request Body:**
```typescript
{
  message: string;        // User's message
  expiryHours?: number;   // Thread expiry (0-24, default 3)
}
```

**Response Body:**
```typescript
{
  messages: string[];     // Array of WhatsApp-formatted messages
}
```

**Error Responses:**
- `401 Unauthorized`: Invalid or expired JWT
- `422 Unprocessable Entity`: Missing or invalid message
- `500 Internal Server Error`: AI model or database error

### 2. Thread Lifecycle

**Thread Identification:**
```sql
SELECT * FROM threads 
WHERE user_id = $1 
  AND source = 'whatsapp' 
  AND last_message_at > NOW() - INTERVAL '$2 hours'
ORDER BY created_at DESC 
LIMIT 1
```

**Thread Creation:**
```sql
INSERT INTO threads (user_id, source, created_at, last_message_at)
VALUES ($1, 'whatsapp', NOW(), NOW())
RETURNING *
```

**Thread Expiry Check:**
```typescript
function isThreadExpired(thread: Thread, expiryHours: number): boolean {
  if (expiryHours === 0) return true; // Always create new thread
  const expiryTime = new Date(thread.lastMessageAt);
  expiryTime.setHours(expiryTime.getHours() + expiryHours);
  return new Date() > expiryTime;
}
```

**Race Condition Handling:**
```typescript
async function getOrCreateThread(userId: string, expiryHours: number): Promise<Thread> {
  return await db.transaction(async (tx) => {
    // Lock the user's thread row
    const [thread] = await tx.select()
      .from(threads)
      .where(and(eq(threads.userId, userId), eq(threads.source, 'whatsapp')))
      .for('update');
    
    if (thread && !isThreadExpired(thread, expiryHours)) {
      return thread;
    }
    
    // Delete expired thread
    if (thread) {
      await tx.delete(threads).where(eq(threads.id, thread.id));
    }
    
    // Create new thread
    const [newThread] = await tx.insert(threads)
      .values({
        userId,
        source: 'whatsapp',
        createdAt: new Date(),
        lastMessageAt: new Date(),
      })
      .returning();
    
    return newThread;
  });
}
```

### 4. Text Splitting

**Algorithm:**
```typescript
function splitText(text: string, maxLength: number): string[] {
  // Try paragraphs first
  let chunks = splitByParagraph(text, maxLength);
  
  // If any chunk is still too long, split by sentence
  chunks = chunks.flatMap(chunk => 
    chunk.length > maxLength ? splitBySentence(chunk, maxLength) : [chunk]
  );
  
  // If any chunk is still too long, split by word
  chunks = chunks.flatMap(chunk => 
    chunk.length > maxLength ? splitByWord(chunk, maxLength) : [chunk]
  );
  
  // Add continuation markers
  return addContinuationMarkers(chunks);
}

function addContinuationMarkers(chunks: string[]): string[] {
  if (chunks.length <= 1) return chunks;
  return chunks.map((chunk, index) => 
    `${chunk} (${index + 1}/${chunks.length})`
  );
}
```

### 5. WhatsApp Formatting

**Converter:**
```typescript
function convertToWhatsAppFormat(markdown: string): string {
  return markdown
    // Bold: **text** → *text*
    .replace(/\*\*(.*?)\*\*/g, '*$1*')
    // Italic: *text* → _text_
    .replace(/\*(.*?)\*/g, '_$1_')
    // Strikethrough: ~~text~~ → ~text~
    .replace(/~~(.*?)~~/g, '~$1~')
    // Code: ```code``` → `code`
    .replace(/```(.*?)```/g, '`$1`')
    // Headers: # Header → *Header*
    .replace(/^# (.*?)$/gm, '*$1*')
    // Lists: - item → • item
    .replace(/^- (.*?)$/gm, '• $1')
    // Links: [text](url) → url
    .replace(/\[(.*?)\]\((.*?)\)/g, '$2');
}
```

## Risk Assessment

| Risk | Probability | Impact | Mitigation |
|------|-------------|--------|------------|
| LLM doesn't follow WhatsApp format | Medium | Medium | Use structured output; test with various prompts |
| Text splitting breaks formatting | Medium | Medium | Use smart splitting; test edge cases |
| Thread race conditions | Medium | High | Use database transactions with row-level locking |
| JWT expires mid-request | Low | Medium | Same as streaming; 401 triggers re-exchange |
| Answer too large for single response | Low | Low | HTTP handles large bodies; pre-split into list |
| WhatsApp formatting not supported | Low | Low | Document limitations; fallback to plain text |
| Thread lifecycle logic duplicated | Low | Low | Extract to shared helper |
| User-configurable expiry not in Meta API | Medium | Low | Use default 3 hours initially; add user preferences later |

## Success Criteria

- [ ] WhatsApp service can call a single endpoint and get a complete answer as a list of messages
- [ ] Thread lifecycle (create/reuse based on user-configurable expiry, default 3 hours) works correctly
- [ ] Authentication uses the same JWT flow (BSUID → apps/auth → JWT → apps/api)
- [ ] Answer text is complete and identical to what streaming would produce
- [ ] LLM (Gemini) returns WhatsApp-formatted text (using structured output/function calling)
- [ ] Response is split into WhatsApp-sized chunks (4096 chars) at paragraph/sentence boundaries
- [ ] Errors are returned as HTTP status codes with JSON error bodies
- [ ] No streaming logic remains in WhatsApp service for answer retrieval
- [ ] Unit and integration tests cover the new endpoint
