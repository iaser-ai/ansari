# air-370 thread — apps/mcp turbo env declarations

- Premise check: the issue says apps/mcp's env vars are "not declared anywhere". In fact `apps/mcp/turbo.json` has declared all nine on `dev` and `start` since c639f7aa (2026-10-28). Real gaps: the README table lacked `RAILWAY_GIT_COMMIT_SHA`, nothing pinned the list, and no proof of hash behaviour existed.
- Derivation: no Zod env schema in apps/mcp (the only z.object is the tool I/O schema). Static reads: `process.env.PORT` and `env.MCP_ALLOWED_HOSTS` / `env.MCP_ALLOWED_ORIGINS`. Dynamic: `setting(env, '...')` in runtime-config.ts (ANSARI_RELEASE, RAILWAY_GIT_COMMIT_SHA, MCP_RESPONSE_MODE, ANSARI_API_BASE_URL, ANSARI_CLIENT, ANSARI_API_AUTHORIZATION). README table: the same set, minus RAILWAY_GIT_COMMIT_SHA (now added).
- Decision: keep per-task `env` on dev/start only, and add no globalEnv. `build` reads none of them (scripts/build.ts bundles no setting). `test` deliberately declares none: tests set what they need, and strict mode keeps a shell's values out of the tests that spread process.env.
- Proof (turbo --dry=json, ansari-mcp#start and #dev): setting MCP_RESPONSE_MODE, RAILWAY_GIT_COMMIT_SHA or ANSARI_API_AUTHORIZATION moves the hash. With MCP_RESPONSE_MODE removed from start.env, the hash is identical set vs unset; restored, it moves again. The dry-run shows ANSARI_API_AUTHORIZATION only as a sha256, never as plaintext.
- Test: apps/mcp/test/turbo-env.test.ts pins dev.env == start.env == README table ⊇ source reads, and bare names only. Negative-tested: dropping a turbo entry, dropping a README row and adding an undeclared source read each fail it.
- PR #371 opened. On owner review, the README paragraph about turbo/test internals was cut: its rationale now lives in the header comment of `test/turbo-env.test.ts` (641731f0). The README keeps only the `RAILWAY_GIT_COMMIT_SHA` row. PR gate approved by the human (relayed by the architect on 2026-11-11), merged as a merge commit.
