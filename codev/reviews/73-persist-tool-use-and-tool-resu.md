# Review: Persist tool_use and tool_result

## Summary

Restored tool-call persistence lost in the Python→TypeScript rewrite: every tool
dispatch the facilitator makes is now durably recorded — on the assistant row's
new nullable `messages.tool_calls` jsonb column, or in a new `tool_call_orphans`
table when the turn ended in error/empty and produced no assistant row — without
touching `content` or any API response byte. Three phases (schema + migration
0007; facilitator accumulation; route wiring + frozen-contract tests), 35 app
files changed, +2,664/−66, suite 73 files / 708 tests green. The mawsuah
degradation rate is now exactly computable over every dispatch, including the
failure-correlated turns the operator explicitly pulled into scope at spec review.

## Deviations from Plan

- **Phase 1 — migration number.** Plan said `0005`; PR #88 merged first and took
  journal idx 5 as `0006_feedback_dedupe_upsert`. Per the architect, I merged
  develop before generating, got idx 6, and named the file/tag
  `0007_tool_calls_persistence` to avoid a `0006_*` filename collision. The
  snapshot is `0006_snapshot.json` (snapshots are idx-named). Consequence for
  the next migration author: drizzle will emit another `0007_*` prefix — name
  it `0008_*`.
- **Phase 1 — read-path projection** (added at plan review, executed as
  planned): `findMessagesByThread` / `getThreadWithMessages` /
  `createThreadSnapshot` project `tool_calls` out, making contract safety
  structural. Single-message lookups (`findMessageById`,
  `findMessageInOwnedThread`) intentionally still return full rows — they feed
  feedback ownership checks, not serialization.
- **Phase 3 — `toolCallsOrNull()` lives in `db/schema/messages.ts`**, not
  `lib/db/threads.ts` as a route-local `?? null` would have implied. Review
  (Codex) caught that `?? null` would persist `[]` for an explicitly empty
  array; placing the pure helper in the schema module avoided touching every
  existing factory mock of the threads module.
- **Phase 3 — Sentry on orphan-write failure** (review-driven, Claude): a lost
  orphan row is the undercount this spec removes, so failures now raise a
  warning-level Sentry message with a non-PII summary in addition to the log.
- **Phase 2 — id format** gained a per-request sequence
  (`tool_<ts>_<seq>_<rand>`) for structural uniqueness (review-driven, Claude).

## Lessons Learned

### What Went Well

- The `done`-event conveyance pattern from issue #70 (`usage`, `rawPayload`)
  extended cleanly to `toolCalls`; one loop-level accumulator covered every
  path — normal rounds, T1/T2 short-circuits, synthesis, retries, limit
  refusals — without touching the wire events.
- Choosing a separate table for error-turn records made invisibility a property
  of the schema rather than of every consumer's discipline; the reviewers
  independently converged on it and the frozen-contract tests were then easy
  to make byte-exact.
- Consultation caught real defects at every level: the error-path denominator
  bias (spec), whole-row reads on the hot path (plan), the untested tool-side
  `degradation` wiring (Phase 2), the `[]`-vs-`NULL` edge (Phase 3).

### Challenges Encountered

- **Migration numbering under concurrent merges.** PR #88 landed between plan
  and implementation, shifting the journal; resolved by merging develop first
  and renaming per the architect's instruction.
- **DDL drift with a merge-timing twist.** Six test files hand-write `CREATE
  TABLE messages`; one (`feedback-upsert.test.ts`) arrived *with* the develop
  merge after my initial grep, and its whole-row select failed loudly (11 tests
  500'd) until the column was added. The #70 lesson holds, with the corollary:
  re-grep DDL sites after every develop merge.
- **Factory mocks hiding a thrown TypeError.** Four route tests factory-mock
  `@/lib/db/threads` without the new `persistOrphanToolCalls` export; vitest
  throws on access to a missing export, but the streams' `catch` swallowed it
  and the suite stayed green. Found only by reasoning about it, not by any
  failure.
- **Facilitator unit tests and lazy config reads.** Two terminal error paths
  (Inkling rescue check, degenerate-final log summary) lazily read validated
  config, which throws without env; each needed a targeted module mock.

### What Would Be Done Differently

- Grep for `vi.mock('<module>'` factories the moment a route gains a new import
  from that module, before running the suite — treat a green run after adding
  an error-path call as unproven until each factory carries the export.
- Do the "fresh DDL grep" as the last step before commit, after any merge, not
  as the first step of the phase.

### Methodology Improvements

- Porch's implement loop required a `porch done` "fix iteration" round-trip
  after REQUEST_CHANGES even when fixes were already committed; a `--fixed`
  shortcut (or detecting the rebuttal file) would save a build/test cycle.
- The review-phase template's `## Consultation Feedback` section is long for a
  six-round project; a per-round table format might read better than nested
  headings.
