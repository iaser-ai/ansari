## Findings

**1. The arrival gate has no deadline, and the poster can now be lost entirely (main issue).**

`shown = settled && !dismissed && (videoExpected ? clip !== 'pending' : true)`, and `clip` leaves `'pending'` only via `onReady` (`ready && primed`) or `onFail` (`status === 'error'`). On web, `ready` needs `status === 'readyToPlay'` or `isPlaying`. I checked `expo-video/build/VideoPlayer.web.js:356-363`: `readyToPlay` is set only from `oncanplay` with `readyState >= 3` — i.e. it requires actual data. So in a context where the browser neither loads data nor errors, nothing ever resolves:

- iOS Low Power Mode suppresses muted inline autoplay *and* defers preload, so `play()` is rejected (silently — the rejection is a promise, not a throw, so the `catch` at `:655-659` can't see it) and `el.preload = 'auto'` doesn't force the fetch.
- `useClipBuffered` times out at 8 s and sets `buffered` anyway, so `primed` arrives — but `ready` never does.
- After that timeout `wantPlaying = running || (web && !clipBuffered)` becomes `false`, which also switches off both the watchdog and the `pointerdown` gesture retry. So a tap after 8 s can no longer rescue it.

Result: on such a phone the whole layer — poster included — never appears. On `origin/develop` the poster came up at settle regardless of the player (its docstring: "a tiny poster still stands in immediately"). Every other wait in this file is capped (settle idle, buffer wait, seek settle); readiness is the one that isn't. A cheap fix in keeping with the design: one arrival deadline that flips `clip` to `'failed'` (poster alone in the same single fade), and/or keep the web `pointerdown` retry armed once `clipBuffered` is true. The review file's "can take longer… capped at 8 s by `BUFFER_WAIT_MAX_MS`" bullet understates this — it isn't only later, it can be never.

**2. The `onFail` test doesn't exercise the failure path** (settled by reading, not by running anything). In `brings the poster in alone when the player fails`, `FakePlayer.play()` sets `playing = true` regardless of `status`, so the warm-up latches `ready`, `primed` lands at 1250 ms, `running` goes true and `onReady` fires — `clip` ends as `'ready'`, not `'failed'`. The `layerOpacity === DAY_STRENGTH` assertion is therefore satisfied by the success path and would still pass with `onFail` deleted. (`expect(player.playing).toBe(false)` *is* genuine — `live` is false so the play effect never runs.) Make `play()` a no-op when `status === 'error'` and additionally assert the inner video host stays at opacity 0; that pins the real behavior. Relatedly, the comment at `:768-771` ("on error it stays hidden for good") holds only because no frames ever arrive to latch `ready` — worth saying so, since `running` is latched and an error *after* arrival leaves the video view at opacity 1 on a frozen frame.

**3. Minor: `clip` isn't reset when `source` changes.** Crossing the desktop breakpoint swaps `source` without remounting `AmbientVideoPlayer`, and `ready`/`primed` stay latched — so the new, unbuffered clip is shown at opacity 1 immediately while the layer stays visible. Rare (window resize), and arguably no worse than before; a `key={source}` on the player would make it re-earn its arrival.

**4. Nit:** `onReadyRef.current = onReady` is a render-phase ref write, and this prototype has `experiments.reactCompiler: true` (`app.json:44`). The compiler bails out of optimizing components that mutate refs during render, so `AmbientVideoPlayer` silently opts out. Assigning inside the effects (or `useEffect(() => { ref.current = cb })`) keeps it compilable. No correctness impact.

Nothing here blocks a human from testing this in a browser or on a phone, and the on-device blind A/B already happened — so I'd proceed, with item 1 as a decision for the human (fix now vs. a follow-up issue) and item 2 as a cheap test tightening.
