## Comments (none blocking)

**1. The Dockerfile pins uv 0.5.11 against a `revision = 3` lockfile.** `Dockerfile:9` copies `ghcr.io/astral-sh/uv:0.5.11`, but `uv.lock:1-2` is `version = 1 / revision = 3` — a lockfile format written by a far newer uv. The `revision` key did not exist in 0.5.x. I could not prove the failure by reading alone (it depends on whether uv 0.5.11's deserializer rejects unknown keys), and nothing in this PR builds the image, so the question is open rather than settled. It's a one-line fix to remove the doubt: bump the tag to a uv that understands revision 3. Separately, `Dockerfile:44`'s second `uv sync` has no `--frozen`, so a deploy can silently resolve away from the lock that CI tested. Both are deploy-path concerns that Phase 4 owns — but Phase 1 lists the Dockerfile in its file set, so it's worth either fixing now or writing down as a named Phase 4 item.

**2. `conftest.py`'s comment overstates what `setdefault` preserves.** "real values still win" holds for exported environment variables, but not for a developer's `.env` — pydantic-settings ranks environment variables *above* dotenv values, and `os.environ.setdefault` writes environment variables. So a developer who sets `MOCK_ANSARI_CLIENT=False` in `.env` to exercise a real backend silently gets the mock instead, which contradicts both `README.md:152` and the module docstring at `test_whatsapp_service.py:15-18`. Either reword the comment or gate the defaults on `.env` being absent.

**3. `test_webhook_message_basic` effectively asserts only "HTTP 200".** At lines 302-318 both the `success and "processed successfully"` branch and the `else` branch call `assert True`. It has more teeth than it looks — Starlette runs `BackgroundTasks` before `TestClient` returns, so an exception in `handle_text_message` would surface — but it will not catch a response that comes back `success: False` with a 200. Since `ALWAYS_RETURN_OK_TO_META` is `False` under test, asserting `response.json()["success"] is True` costs one line and makes the happy path actually tested. This is imported legacy test style, so I'd leave it to whenever that suite is rewritten rather than ask for it now.

**4. `/sentry-debug` (`main.py:111-113`) is unauthenticated and present in every environment.** Deliberate legacy behaviour for verifying Sentry wiring, and harmless beyond a 500, but worth a note before this reaches production in Phase 4.

**5. `clean_logs.sh` looks like the kind of personal script Phase 1 said to exclude** ("without its logs, `tmp/` files, personal scripts..."). Minor — flagging only because it's the one file in the import that the plan's exclusion list arguably covers.

**6. The `whatsapp` check is not a required check on `develop`.** The workflow header notes branch protection is an admin-coordinated change (lines 113-120). The job will run on PRs, but nothing blocks a merge on it failing until someone makes it required. Worth surfacing to the human rather than fixing in code.
