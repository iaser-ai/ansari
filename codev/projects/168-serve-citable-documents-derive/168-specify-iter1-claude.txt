## Issues

**1. Factually wrong assumption about `v1/chat/completions`.** The spec's Assumptions say assistant messages from mcp-complete *and* v1/chat/completions "persist through the same facilitator records." `mcp-complete/route.ts:234` does pass `toolCalls: toolCallsOrNull(toolCalls)`. **`v1/chat/completions/route.ts:371-382` does not persist `toolCalls` at all** — no such field in the `createMessage` call, and `collectResponse` there doesn't thread them. Leaderboard threads will therefore never yield documents. Harmless outcome, wrong premise; correct the sentence so nobody plans or tests against it.

**2. The "existing contract tests stay unmodified" mitigation is false, and it points the builder the wrong way.** `tests/thread-get-contract.test.ts:65,194` asserts `expect(Object.keys(m)).toEqual(MESSAGE_KEYS)` — exact set *and* order. Any message gaining `documents` fails it. Two consequences the spec must address:
   - **Specify where `documents` sits** in the serialized message object (append last, or immediately after `content`). This is exactly the contract detail the frozen test pins; leaving it unstated invites the builder to *loosen* `MESSAGE_KEYS` (e.g. to a subset check) rather than assert the new exact shape — a direct hit on the paramount constraint.
   - The seeded `RECORDS` fixture (line 55) has no `result_meta`, so under fail-closed the extended `TOOL_KEY_PATTERN` scan for `result_meta` would pass **vacuously**. Require a `result_meta`-bearing seed so both the key-set assertion and the scan are live — consistent with the negative-test discipline the spec otherwise applies well.

**3. Doc-contradiction scope is too narrow.** Constraint 3 and the criteria name only `arch-critical.md` / `arch.md`. The same absolute wording is in code: `db/schema/messages.ts:102-106` ("no serializing or replay path selects it"), `lib/db/threads.ts:20-31` ("...and avoids detoasting ~7 KB median of jsonb per assistant row"), `lib/db/shares.ts:30-32`. Per your own lessons-critical ("fix a documentation defect everywhere"), add these to the success criteria.

**4. No runtime validation requirement for the jsonb.** `ToolCallRecord.content` is `Record<string, unknown>` — `$type<>` is a compile-time fiction over untyped jsonb. The spec fails closed on `result_meta` length mismatch but says nothing about a malformed `results` (not an array, entry missing `title`/`content`, non-string values). Add a criterion: derivation validates each entry structurally and drops what doesn't validate — never emits `{title: undefined}`.

**5. Two smaller items for the plan.** (a) The budget-skip record is built **inline** at `agent.ts:931`, not via `buildToolResultRecord` — `result_meta` must be handled at two sites (fail-closed makes it safe, but say so). (b) State that the derivation helper is only reachable after the existing ownership check in thread GET, so it can't become an unscoped read path.

I made no changes to the tree.
