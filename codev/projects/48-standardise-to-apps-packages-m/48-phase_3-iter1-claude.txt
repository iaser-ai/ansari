## One real defect: the shared config is invisible to the cache key

This phase is the first time an app's compilation depends on a file **outside its own package**, and Turbo does not hash it. Verified empirically (`--no-daemon`, `--dry=json`):

| action | `ansari-api#typecheck` hash |
|---|---|
| baseline | `dfd6e1c37502af0e` |
| add `forceConsistentCasingInFileNames` to `packages/tsconfig/base.json` | `dfd6e1c37502af0e` — **unchanged** |
| control: add a file under `apps/api/lib/` | `a1c6cf6fa99b16b3` — changed |

The control proves the method. Cause: `@ansari/tsconfig` defines no tasks, so it never enters the task graph and its files never enter any task hash; `globalDependencies` covers only `pnpm-lock.yaml` / `pnpm-workspace.yaml`, and the lockfile's `link:` entry doesn't change with file contents.

Consequence: edit the shared compiler options, run `pnpm typecheck` → **cache hit, green, no signal**. Same failure shape phase 2 treated as unacceptable for `env` ("a cache key that ignores a value baked into the artifact"), now for files. CI is unaffected today only because `.turbo` isn't cached there (architect decision 5) — that's an accident of configuration, not a guard.

**Verified fix** (I tested it, then reverted): adding `"packages/tsconfig/base.json"` to `globalDependencies` makes the hash move (`8c439ab5f4807a74` → `266874037d3c4552`). Alternative, more precise on turbo 2.10.11: `"inputs": ["$TURBO_DEFAULT$", "$TURBO_ROOT$/packages/tsconfig/base.json"]` on `typecheck`/`build`. Phase 4's `@ansari/eslint-config` has the identical gap for `lint`, so a glob covering `packages/**` may be the cleaner single answer — but prove it in both directions (hash moves on edit; and confirm you didn't just make everything permanently dirty).

Minor nit: `@ansari/tsconfig` is inserted after `tsx` in `apps/api/package.json` devDependencies, breaking alphabetical order (frontend is sorted correctly).
