## Issues worth folding in before implementation

**1. Whole-row reads now drag the tool payloads through the hot path.** `findMessagesByThread` (`lib/db/threads.ts:89-95`) does `select()` — every column. Both chat routes call it on *every turn* to rebuild history (`route.ts:164`, `chat/route.ts:66`), and `createThreadSnapshot` (`shares.ts:31-35`) does the same. Today that pulls `raw_payload` needlessly; after this change each assistant row also carries ~7 KB median (up to ~70 KB for a 10-dispatch turn) of detoasted jsonb that is then thrown away by the `.map()`. A long thread turns into hundreds of KB read per request for nothing. The plan never mentions this. The fix is one line per query — explicit column projection in `findMessagesByThread`/`getThreadWithMessages`/`createThreadSnapshot` that omits `tool_calls` — and it has a second payoff: the frozen-contract guarantee stops depending on the routes' `.map()` discipline and becomes *"the column is never selected on any serializing path."* That is strictly stronger than the regression test the spec asks for, and it complements rather than replaces it. Worth adding as a Phase 3 (or Phase 1) deliverable.

**2. mcp-complete's throw→return refactor has no contract acceptance criterion.** `collectFacilitatorResponse` currently `throw`s on an `error` event (`mcp-complete/route.ts:103`), and that throw propagates to the POST/GET catch, producing a **500 with the facilitator's error message** as the body. Converting to return-based control flow (which the plan correctly requires, to stop losing the records) silently rewires that path. The plan pins the 502 empty-answer behavior but says nothing about the facilitator-error 500. Add an explicit criterion: *status code and body for a facilitator `error` on mcp-complete are unchanged.* `mcp-complete.test.ts` exists to extend.

**3. `degradation` will sometimes be absent on a degraded result.** The tools build `meta = {}` when the caught error is not a `ToolFetchError` (`search-quran.ts:121-124`), and the `agent.ts:228-236` backstop knows only `errorClass: 'network'` with no attempts. So `status: 'degraded'` with no `error_class` is a legitimate state. Phase 2's acceptance criterion reads as though `error_class` is always present — make the field optional in both the type and the criterion, or the builder writes a test that can't hold.

**4. T1 and T2 skips collapse into one status.** Both the degraded-threshold short-circuit and the wall-clock backstop write `budget_skipped`. The spec fixes the *category set*, but leaves field names open — recording the trigger (`skip_trigger: 'T1' | 'T2'`) as an extra field costs nothing and preserves the distinction between "we stopped because the provider was down" and "we stopped because we ran out of time," which is squarely the reliability signal this feature exists to produce.

**5. Minor:** state that the orphan write happens *after* `safeClose()` on the streaming error paths, so bookkeeping can't delay the client's error delivery. The plan's risk table covers the failure-masking case but not the latency ordering.

Phase sizing and sequencing are sound — each phase is independently committable (Phase 2 accumulates records that nothing yet persists, which is harmless), dependencies are respected, and the test strategy correctly uses pglite through real helpers rather than mocks, per `lessons-critical.md`.
