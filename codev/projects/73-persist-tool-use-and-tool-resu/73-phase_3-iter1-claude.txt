## Non-blocking observations

1. **Post-close async durability (COMMENT).** On the two streaming routes the orphan write runs inside `start()` after `controller.close()`. On Railway's long-lived Node process the promise settles normally, so this is fine as-shipped — but it's an implicit platform assumption. If this app ever runs somewhere that tears down the request context at response end, those writes vanish silently (and `persistOrphanToolCalls` swallowing errors means you'd never see it). Worth one sentence in the arch-doc update during review phase.

2. **Orphan-write failures are console-only.** `persistOrphanToolCalls` logs but doesn't `Sentry.captureMessage`. Swallowing is correct (per plan); but a systemic failure of this write is exactly the silent-undercount failure mode the spec exists to prevent, and the metric would quietly skew again. A count-only Sentry message (no user content) would make it loud. Minor, and arguably a follow-on.

3. **`runFacilitator` throwing rather than yielding `error` loses records** on all three sites. I checked `agent.ts` — the loop body's catch converts throws into terminal `error` yields (`agent.ts:993-999`) and max-iterations yields with records, so the only uncovered throws are pre-loop setup ones, which precede any dispatch. Residual risk is effectively zero; noting it only so it's a known boundary rather than an assumption.

None of these block the phase.
