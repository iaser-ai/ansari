## Gaps

**1. The four tool-file changes are untested production code.** The only change in `search-{quran,hadith,mawsuah,tafsir}.ts` is `unavailableResult(label)` → `unavailableResult(label, meta)`. Nothing anywhere asserts that a real degrade produces `result.degradation`. `facilitator-toolcalls.test.ts` stubs `run()` to return `unavailableResult(name, {errorClass:'timeout', attempts:2})` directly — that proves the facilitator reads the field, not that any tool populates it. `grep degradation apps/api/tests` returns zero assertions on `ToolResult.degradation`. If someone reverts one of those four lines, every persisted mawsuah record silently loses `error_class`/`attempts` and the suite stays green — which is the exact metric this spec exists to make trustworthy.

The plan's Phase 2 Test Plan names this explicitly: *"a resilience-level test that a retried-timeout degrade yields `degradation.attempts === 2` end-to-end into the record."* `usul-retry.test.ts:144-162` already exercises the 5xx degrade through the real tool and asserts `isDegraded` — adding `expect(result.degradation).toMatchObject({ errorClass: 'http_5xx', status: 502, attempts: 1 })` there, plus the equivalent on the timeout-retry case and one in `kalemat-resilience.test.ts`, closes it in a few lines.

**2. Two of the four enumerated terminal-error paths have no test.** The plan's risk table mitigates "Terminal-yield coverage gaps" with *"dedicated test per path (degenerate-final, synthesis, catch-all, max-iterations)."* The suite covers synthesis (line 352) and catch-all (line 342) but not **degenerate-final** (agent.ts:777) or **max-iterations** (agent.ts:1000). Both are reachable with the existing harness — degenerate-final needs `doneResponse` extended with a `finishReason` (e.g. `'SAFETY'`); max-iterations needs 10 `toolRound` scripts.

## Minor (non-blocking)

- **Id minting** (agent.ts:415): `tool_${Date.now()}_${Math.random().toString(36).slice(2,7)}` — two dispatches in the same ms could in principle collide, and `.slice(2,7)` occasionally yields fewer than 5 chars. A monotonic per-request counter (`tool_${++n}`) would make in-array uniqueness structural at zero cost. Analytics only needs uniqueness within the array, so this is a nit, not a bug.
- **Unpaired-record tolerance**: `recordToolUse` fires before dispatch (deliberate, and right). But `createToolMap()` runs before `processToolCall`'s try — if it throws, the array ends with a `tool_use` and no `tool_result`. Analytics queries shouldn't assume strict pairing. Worth a line in the arch-doc note during review phase; the test helper `pairs()` currently encodes the stricter assumption.
- The T2 test uses a 60ms `slow_ok` tool but never asserts `duration_ms` is in a plausible range — a cheap strengthening of the timing instrumentation.
