## Non-blocking observations

1. **`deleteExpiredTokens` uses `.returning()` for a row count only.** `users.ts:329` materializes every deleted row (all columns, including `token_hash`) just to read `result.length`. This was harmless while the function was dead code; Phase 9 makes it live against a table that has grown unbounded since inception, so the *first* production sweeps could pull a very large row set into app memory. `.returning({ id: tokens.id })` is a one-line mitigation.

2. **No index on `tokens.expires_at`.** `db/schema/tokens.ts:14-17` indexes only `token_hash` and `(user_id, token_type)`, so each sweep is a seq scan. The plan's own risk mitigation says "low probability + **indexed** delete" — the indexed half isn't there. Migration `0003` hasn't been applied to prod yet, so adding the index is still cheap if you want it; otherwise it's an accepted cost given the 2% gate and fire-and-forget execution.

3. **The sweep wiring itself is untested.** All three route tests stub `maybeSweepExpiredTokens: () => undefined`, so the probability gate and the `.catch()` error-swallow (which is what keeps a sweep failure from becoming an unhandled rejection) have zero coverage. A ~5-line unit test mocking `Math.random` would lock both in.

4. `reset_password`'s `.max(128)` has no direct test (register's does). Minor symmetry gap.

None of these block the phase: the acceptance criteria ("leaderboard compare is constant-time; password policy is `score>=3` + `.max(128)`; register error is generic with detail logged; `deleteExpiredTokens` runs and honors retention") are all met, with the required test rewrite done and no scope creep into the deferred list.
