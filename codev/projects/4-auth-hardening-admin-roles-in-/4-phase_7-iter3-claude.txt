## Observations (non-blocking)

1. **The security argument rests on an undocumented invariant.** The plan pinned "capture the version at auth time, don't re-read inside the tx"; the implementation re-reads inside the tx (`refresh_token/route.ts:50`). I traced this and it is **sound** — under READ COMMITTED the recheck's join is snapshot-consistent, so a refresh can only observe the *new* version if the revoking transaction already committed, in which case the refresh row is gone and `recheck.status !== 'valid'`. But that holds **only because every `bumpSessionVersion` caller revokes tokens in the same transaction** (reset `:64-71`, logout `:19-22`, `grant-admin.ts:59-70`). A future caller that bumps the version *without* revoking in the same tx silently reopens the race. Worth one comment line at `refresh_token/route.ts:44` or on `bumpSessionVersion` stating that invariant.

2. **`findToken` has no `exec`** — the plan listed it. Deliberate and fine (it's never called inside a transaction; the transactional path uses `lookupRefreshToken`). Already accepted by prior reviewers.

3. **`deleteExpiredTokens` (`users.ts:324-339`) still deletes rotated-past-grace rows**, contradicting the retention rule reuse detection depends on. Correctly deferred — Phase 9 owns the flip plus the `token-grace.test.ts:151` rewrite, and the sweep has **no production caller today** (grep confirms: definition + one test). Nothing regresses now; must not be lost.

4. **Reuse warning carries no identifier** (`refresh_token/route.ts:30`), so an operator seeing it can't correlate. A hashed user id would stay within the no-user-content rule. Optional.

5. **Commit hygiene:** Phase 7's code landed across three `chore(porch): … build-complete / re-iter` commits (`d124945`, `a34aeb2`, `ca9e918`) rather than a `[Spec 4][Phase: …] feat:` commit like Phases 5 and 6 got. Worth a proper phase commit before the PR to match the plan's "one atomic commit per phase."
