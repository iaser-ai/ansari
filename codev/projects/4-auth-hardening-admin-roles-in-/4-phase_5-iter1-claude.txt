## Non-blocking observations

1. **`catch { … }` in `getOrCreateSystemUser` (users.ts:65) swallows the original error entirely.** Any insert failure — DB unreachable, missing column, a not-yet-applied migration — falls into the same branch and surfaces as *"its address is already held by a non-system account"*, which is actively misleading during an incident. The plan's deliverable also says the failure should be **logged**; today it only throws. Suggest `catch (error)` → `console.error('[system-account] provisioning failed', error)` and `new Error(msg, { cause: error })`.

2. **The fail-fast message reaches unauthenticated callers on `mcp-complete`.** That route's outer handler returns `error.message` in the 500 body (`mcp-complete/route.ts:195`), so a hijack condition would echo the internal wording publicly. Minor disclosure; Phase 9 already lists "System routes' `error.message` leakage may be addressed here too if low-cost" — flagging so it isn't forgotten. (`v1/chat/completions` is safe: its logging block is non-fatal try/caught.)

3. **The `raced` re-read branch (users.ts:68-69) has no direct test.** The idempotency test exercises the early-return path (`findSystemUser` hits first), never the catch→re-read path. The plan's test plan called for "idempotency (existing-row race) **and** fail-fast (occupied email) **branches**". A one-liner mocking `findSystemUser` to miss once would close it.

4. **Docs don't mention the reserved system domain.** `docs/self-hosting.md:66` documents `ADMIN_EMAILS` reservation well, but nothing tells a self-hoster that `*@system.ansari.chat` registration is permanently refused (hardcoded, not configurable). One line under "Provisioning admins" would cover it.

None of these affect the security properties this phase exists to establish: system identity is now resolved solely by the unregisterable `system_key`, a pre-registered look-alike is provably never resolved, and registration of the system domain is indistinguishable from an ordinary conflict.
