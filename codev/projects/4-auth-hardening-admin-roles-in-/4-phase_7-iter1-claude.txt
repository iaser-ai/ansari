I read the implementation files from disk, ran `npm run typecheck` (clean) and `npm test` (58 files / 549 tests green).

### What's correct

**Executor threading** (`lib/db/users.ts`) — the plan's #1 risk ("`db.transaction()` is a no-op unless inner helpers use the `tx` handle") is addressed properly. `updateUser:128`, `bumpSessionVersion:148`, `storeToken:169`, `issueTokenPair:192`, `markTokenRotated:256`, `lookupRefreshToken:282`, `deleteUserTokens:314` all take `exec: Executor = db` and use it. No helper on the rotation/reset path silently closes over the module-level `db`.

**Atomic rotation** (`refresh_token/route.ts:43-48`) — `markTokenRotated(tx)` + `issueTokenPair(tx)` inside one `db.transaction`. `deleteToken` is gone; issue #34 grace semantics preserved.

**Capture-at-auth-time** — this is the subtle part and it's right. `validateRefreshToken` returns the user read *before* the transaction (`route.ts:26`), and `issueTokenPair(user.id, user.sessionVersion, tx)` receives that captured value; `issueTokenPair` explicitly never re-reads it (`users.ts:196-199`). Under READ COMMITTED, a reset committing mid-refresh leaves the newly-minted pair carrying the pre-reset version → rejected. The reverse ordering is covered by the token deletion. Correct on both interleavings.

**Session version** — additive optional claim (`jwt.ts:13`), equality check with `?? 0` on both paths (`middleware.ts:66`, `middleware.ts:105`), piggybacking the existing join. Reset applies `updateUser` + `bumpSessionVersion` + `deleteUserTokens` in one transaction (`reset_password/route.ts:60-64`).

**Reuse detection** — `lookupRefreshToken` (`users.ts:282-303`) is a clean four-state machine keyed on `token_type='refresh'`, with natural-expiry checked *before* the grace comparison so past-expiry reads as `not_found` rather than `reuse`. Reject + `console.warn` with no user content and no raw token (`route.ts:30`) — matches the pinned "reject + log only, no version bump" decision.

### Issues

**1. No real-DB test proves the executor threading / transaction atomicity.** Both transactional routes are tested with `db: { transaction: async (cb) => cb({}) }` (`refresh-token-route.test.ts:37`, `password-reset.test.ts:24`) *and* fully mocked helpers. A helper that ignored its `exec` and wrote through the global `db` would pass every test in the suite. The plan lists this explicitly as a deliverable — *"Unit: executor threading (helper called with `tx` writes within the transaction)"* — and it's the risk table's highest-impact row. `session-version-reuse.test.ts` already has a real pglite `db` and the real helpers; ~15 lines there would close it:

```ts
await expect(db.transaction(async (tx) => {
  await markTokenRotated(t, tx);
  await issueTokenPair(USER_ID, 0, tx);
  throw new Error('boom');
})).rejects.toThrow();
// assert: rotated_at still NULL, no new token rows
```
The plan also asked to *"verify `db.transaction()` interacts cleanly with the existing pglite hand-DDL patterns (ensure no deadlock/hang)"* — currently no Phase-7 test executes a real `db.transaction` at all. (`grant-admin.ts:59` does, against pglite, but with raw `tx` queries, not these helpers.)

**2. Only one reset-vs-refresh ordering is tested, and the reset transaction has no real-DB coverage.** The plan requires *"reset-vs-refresh interleavings (both orderings) as deterministic sequences."* `session-version-reuse.test.ts:146` covers reset-commits-then-stale-issue; the reverse (refresh commits first → reset revokes + bumps → both the old and the just-minted pair are dead) isn't asserted anywhere, and `password-reset.test.ts` mocks `updateUser`/`bumpSessionVersion`/`deleteUserTokens`/`db.transaction`, so nothing verifies the reset actually bumps and revokes together against a real DB.

### Non-blocking notes

Correctly deferred — Phase 9 owns the retention flip and the test rewrite, and the sweep isn't wired to any caller yet, so nothing regresses today. Flagging only so it doesn't get lost.
