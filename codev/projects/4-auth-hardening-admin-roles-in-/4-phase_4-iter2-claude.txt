### Blocking issue

**`grantAdmin` promote path resets the password but does not revoke the promoted account's existing tokens** (`scripts/grant-admin.ts:51-59`).

The iter-1 rebuttal claims resetting the password "locks the attacker out." It does not, on its own. Concretely:

1. Attacker pre-registers `admin@ansari.chat` today (the live vector this spec closes) and logs in → holds an access token (≤2h) and a **refresh token valid 90 days**, rows in `tokens`.
2. Operator applies the migration and runs `grant-admin.ts admin@ansari.chat` → row is promoted to `is_admin=true`, password overwritten.
3. The attacker's tokens are untouched. `findToken` still resolves them, `authenticateRequest` returns the now-`isAdmin=true` user, and `requireAdmin` grants → the attacker reads `/api/v2/admin/stats` (all users' message previews) and can mint fresh access tokens for 90 days.

The bootstrap is the *one* privileged provisioning path in this phase, and this is exactly the pre-registration scenario it exists to defuse. The fix is one line on the promote branch, and it matches the codebase's own convention — `src/app/api/v2/reset_password/route.ts:59` already calls `deleteUserTokens(user.id)` on a password change:

```ts
if (existing) {
  await db.update(users)
    .set({ isAdmin: true, passwordHash, updatedAt: new Date() })
    .where(eq(users.id, existing.id));
  await deleteUserTokens(existing.id); // revoke any pre-existing sessions (pre-registrant lockout)
  return { created: false };
}
```

Note this won't be fixed incidentally by Phase 7 — `session_version` lands there, but nothing in Phase 7 touches `grant-admin.ts`. Please add a test asserting a seeded token row for the promoted user is gone after promotion.

### Non-blocking comments

1. **`docs/self-hosting.md:66` is now misleading and operationally hazardous.** It still reads *"`ADMIN_EMAILS` | empty | Comma-separated allowlist for the admin dashboard."* After this phase, setting `ADMIN_EMAILS` **grants nothing** and **hard-fails production boot** until `grant-admin.ts` has run. An operator following current docs will ship a crash-looping deploy. The plan tracks this under "Documentation Updates Required" (plan-level, pre-PR), so I'm not blocking on it — but it's cheapest to write while the semantics are fresh: allowlist = *reserve + assert*, DB flag = *authorize*, and the runbook ordering migration → bootstrap → deploy.
2. **DB-unreachable at boot is indistinguishable from missing-admin.** `assertConfiguredAdminsExist` lets a connection error propagate raw, so a transient DB outage surfaces as an opaque boot crash rather than the clear "run grant-admin" message. The spec's Notes asked the plan to "note graceful behavior if the DB is transiently unreachable at boot." Wrapping the `findUserByEmail` call and rethrowing with "admin bootstrap check could not reach the database" would make on-call triage much faster. Railway's restart loop means it self-heals; this is purely diagnostic.
