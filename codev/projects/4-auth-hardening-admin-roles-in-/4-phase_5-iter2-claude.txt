## Non-blocking observations

1. **The new fail-fast message reaches unauthenticated clients on `mcp-complete`.** `mcp-complete/route.ts:195-196` returns `error.message` in a 500 body, so a hijacked-email deploy would emit `"System account 'ai-skill' cannot be provisioned: its address is already held by a non-system account…"` publicly. Not a Phase 5 regression (the leak predates it), and Phase 9 explicitly scopes "System routes' `error.message` leakage may be addressed here too" — but Phase 5 gave that leak a more interesting payload, so please make sure Phase 9 actually takes it. Note the `v1` path is fine: `getSystemUserId()` sits inside the non-fatal logging `try` (`route.ts:307-324`), so it degrades to a logged Sentry event with no misattribution.

2. **No test wires the real `isReservedAddress` through the register route** — `register-newsletter.test.ts` mocks it via `h.reserved`. The helper is unit-tested and the route's placement is tested, so behavior is covered, but a wiring regression (e.g. someone swapping in a helper that drops the system domain) would pass. One assertion against the unmocked helper would close it.

3. **Misleading message for an unbackfilled-but-legitimate row.** If a legit system row exists with `nologin`/correct `source` but `system_key IS NULL` (migration applied without the backfill matching), the thrown error says "held by a non-system account". Worth a clause pointing the operator at the `system_key` backfill.

4. **Docs**: `docs/self-hosting.md` documents the admin reservation but not that `@system.ansari.chat` is refused at registration. The runbook's inspect-before-apply step mentions "admin/system", so this is minor — it fits the plan's global Documentation Updates item.

None of these block the phase.
