## Non-blocking observations

1. **`grant-admin` promote path is non-transactional** (`grant-admin.ts:54-62`): the `UPDATE` commits before `deleteUserTokens`. If the delete fails (DB blip), you're left with `is_admin=true` and the pre-registrant's tokens still live, and the operator only sees an error. Suggest wrapping both in `db.transaction()`. Related follow-up: once Phase 7 lands `session_version`, this script should also bump it — that's the primitive that closes the narrow rotate-during-the-window race that token deletion alone can't.

2. **Docs omit that the script doesn't load `.env`** (`docs/self-hosting.md:91`). I confirmed: running it from `backend/` with a `.env` present fails with `Environment validation failed` (it needs `DATABASE_URL`, `JWT_SECRET`, `KALEMAT_API_KEY`, `USUL_API_TOKEN`… since `config.database.url` parses the whole schema). The failure is loud and self-describing, so it's a papercut, not a hazard — but a one-line `env $(grep -v '^#' .env | xargs) …` or `railway run …` hint in step 2 would save an operator a confusing minute at the exact moment they're mid-deploy.

3. **`isReservedAddress` requires pre-normalized input** — a footgun with one caller today, and the builder already logged the plan to fold normalization into the helper in Phase 5 when the second call site arrives. Reasonable; just don't let it slip.

4. **Coverage shape**: both `admin-auth.test.ts` and `admin-stats-endpoint.test.ts` mock their boundary (`authenticateRequest` / `requireAdmin` respectively), so no single test proves a real token → real `is_admin=false` row → 403 end-to-end. The seam is thin and type-checked, so this is a note rather than a gap worth blocking on.
