### On the security design

I traced the concurrency claims rather than trusting the review doc, and **the race analysis holds up**. The key invariant is that *every* `session_version` bump site (reset, logout, `grant-admin` promotion) also deletes tokens **in the same transaction**. So refresh's in-transaction recheck either sees `(version=N, tokens present)` or `(version=N+1, tokens gone)` — never a torn state. Tokens minted by a refresh that interleaves with a revocation embed the pre-bump version and fail the version check. That's a correct backstop, and using one uniform primitive for reset/logout/promotion is a genuinely good design choice.

The anti-oracle work is also right: the reserved-address check sits *before* the strength check in `register`, so a reserved address can't be distinguished by status code. That placement detail is easy to get wrong.
