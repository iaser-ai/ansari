## (A) The seven blocking items

1. **Eligibility of the resolved user** — **Closed.** All four conditions (sole account row, noreply domain, `registered_via`, not admin) are re-read under the lock, with an alert and an eligibility matrix covering email/service/admin/promoted/altered users.
2. **Ban check before the lock** — **Closed.** The ban check now sits after the under-lock re-read, and `users.isBanned` (honouring `banExpires`) already exists in `packages/auth/src/users.ts`, so the mechanism is real.
3. **Session creation / token handling / signing** — **Not fully closed.** The session half is specified. The signing half is wrong in one verified detail: `auth.api.signJWT` takes `{payload, overrideOptions}` and never calls `definePayload`; `signJWT` in `dist/plugins/jwt/sign.mjs:107-116` sets `exp`/`iss`/`aud`/`sub` but sets `iat` **only if the caller passes it**, whereas `/api/auth/token` goes through `getJwtToken` (`sign.mjs:118-128`), which injects `iat` and applies `definePayload`. So an exchange token built as the spec describes carries **no `iat`** — distinguishable from every other apps/auth JWT, against this spec's own constraint. It does not break first use (`apps/api/lib/auth/verify-jwt.ts:138` requires only `exp, sub, sid`), so this is a precision fix, not a redesign: pass `iat`, and make the criterion assert **claim-set equality**, not just `alg`/`iss`/`aud`/lifetime. Second-order: hand-building `{sub, sid}` at the exchange duplicates `definePayload` (`packages/auth/src/index.ts:355`) with nothing pinning them together — add a test that both paths produce the same claim set.
4. **Pre-401 outage check missed an unapplied migration** — **Closed** (a query on the relation itself, not `select 1`), with the cache window and the recover-between residual stated honestly. The boot assertion added alongside it opens a new gap (B2).
5. **Missing service user looked like a revoked key** — **Closed.** 500 + alert, never 401; also distinguished from "another owner → 401". `verifyApiKey` returns the key row minus the hash (`index.mjs:~2010`), so `referenceId` is available without a second read.
6. **"`start` not stored" had no mechanism** — **Closed.** `startingCharactersConfig.shouldStore` is real in 1.7.7 and gates the assignment (`index.mjs:808`, default `true` at `:2346`).
7. **Blocked-path prefix claim** — **Closed.** Current State now matches `apps/auth/src/middleware/blocked-paths.ts:56`: only `ADMIN_PREFIX` is prefix-matched, everything else exact. The new `/api/auth/api-key` prefix rule is the right shape. The derivation count is wrong, though — see B5.

## (B) New gaps the revision introduces

**B1. The "No CORS" claim has no mechanism and contradicts the wiring the spec itself records — blocking.**
`app.ts:60` does `app.use(corsFor(getEnv().CORS_ORIGIN))` as the first middleware, and `corsFor`'s origin callback (`middleware/cors.ts:27-31`) decides on **origin membership alone, never path**. A request to `/api/whatsapp/session` carrying `Origin: <configured CORS_ORIGIN>` will therefore get `Access-Control-Allow-Origin` echoed, and the `cors` package will answer the `OPTIONS` preflight before the route is reached. The spec asserts "the global `corsFor` does not apply to this route" as if it were a fact; two paragraphs earlier it correctly says the middleware is mounted globally ahead of every route. This is the same species as iteration 1's prefix-matching defect: a claim with no mechanism. The fix isn't free either — re-ordering or path-scoping a global middleware in an auth service has blast radius on sign-in's CORS and on `mergeExposedHeaders`, so the spec should name the mechanism (path-scoped mount, or an exchange-local header-stripping middleware) rather than leave the builder to discover it when the criterion fails.

**B2. The boot assertion conflates "relation missing" with "database unreachable" — blocking.**
`apps/auth/src/index.ts` deliberately does **zero** database work before `listen()` — the comment at lines 15-17 records the owner amendment that removed the boot admin check precisely so "a stale list can never stop sign-in", and `createDb` connects lazily (`db.ts:9-10`). The spec adds "asserts that `auth.apikey` exists and refuses to start if it does not" with no distinction between a deterministic schema fault and a transient connection fault. A database blip during a deploy would then stop the whole service — sign-in, JWKS, account endpoints — not just the exchange, and under a capped restart policy one blip becomes a permanent outage (this is a named critical lesson in `lessons-critical.md`). Make the assertion fail **only** on a relation-missing error code (`42P01`), treat unreachable as "start and let `/health` report 503", and add the converse success criterion — otherwise the fail-loud guard is strictly a new availability risk to the one thing that must not go down.

**B3. The per-user budget's executor is unspecified, and the refusal path can roll it back — blocking.**
`consumeWindow` (`packages/auth/src/rate-limit-store.ts:31`) is a single upsert on `auth.rate_limit` against whatever `Db` it is handed; the existing precedent (`routes/account.ts:142`) calls it on the pool, **before** the handler and outside any transaction. The spec places it as step 5 *inside* the locking transaction without saying which executor it gets. If it gets the transaction, then returning 429 (and every other refusal: 403, 500, eligibility) rolls the counter back, so the budget never accumulates and never binds — a limit that passes by not running, which is the exact failure mode `lessons-critical.md` warns about. If it gets the pool, it is correct (no FK to `auth.user`, so no lock interaction) but then it is not protected by the lock, which the spec should say out loud. Pin the executor and add a criterion that the counter survives a refused request.

**B4. The `FOR UPDATE` / `KEY SHARE` hazard is correctly identified but has no containment, only a probe — should-fix (high).**
The analysis is right: a session insert's FK takes `FOR KEY SHARE` on the parent user row, which conflicts with `FOR UPDATE` held by another connection, and because the holder isn't waiting, Postgres sees no cycle and will not break it — the request hangs until a timeout that the spec never specifies. `createDb` uses a default `pg` pool (`max: 10`), shared by every route, so ten hung exchanges stall sign-in and JWKS too. Two concrete improvements: (a) require a `lock_timeout`/`statement_timeout` on the exchange's transaction so the worst case is a 500 rather than pool exhaustion; (b) consider `SELECT … FOR NO KEY UPDATE` instead of `FOR UPDATE` — it does **not** conflict with `FOR KEY SHARE`, so the hazard disappears by construction, while still conflicting with a concurrent `DELETE` (which takes `FOR UPDATE` strength) and with the ban `UPDATE` (`FOR NO KEY UPDATE`). That preserves every race the spec needs serialized and demotes the probe from gate to confirmation.

**B5. "Derived from `apiKey().endpoints` and asserted to have length 5" is false — should-fix.**
Probed from the installed plugin: `Object.keys(apiKey().endpoints).length === 7`, and two of them (`verifyApiKey`, `deleteAllExpiredApiKeys`) have `path === undefined` because they are built with `createAuthEndpoint.serverOnly` (`index.mjs:864`, `:1951`), which takes no path. `ADMIN_PATHS` maps `endpoint.path` over all values (`packages/auth/src/index.ts:140`), so copying it "exactly" yields seven entries, two `undefined`, which would flow into both `disabledPaths` and `BLOCKED_EXACT` as garbage. The guard fails loudly in the right direction, so it can't ship silently broken — but the spec should state the filter and assert **both** numbers (7 endpoints, 5 routed), since that pair is what actually detects a plugin bump. Happily, this also confirms the separate criterion "`/api-key/verify` has no route."

**B6. 500 for an ineligible user leaves a permanently bricked BSUID and mis-signals to the consumer — should-fix.**
The choice is defensible for the oracle reason, but it collides with the consumer contract written three sections earlier: "treat 500 as 'apps/auth is failing'". For an ineligible user the condition is permanent and purely local, so the WhatsApp service will retry and page the operator forever for one user while apps/auth is perfectly healthy — and those 500s will sit in the same bucket an operator watches for real outages. Either give the consumer a documented terminal status for this case, or keep 500 and add two things the spec currently lacks: an explicit statement that these 500s are expected to be non-retryable, and a runbook step for what the operator does when the eligibility alert fires (today the alert has no response procedure, and the user stays bricked).

**B7. The alerts contract contradicts itself on identifiers — should-fix.**
The Alerts criteria are headed "counts only, no identifiers", yet the eligibility alert carries "user id only" and the script events carry key ids. `apps/auth/src/alerts.ts` establishes the opposite posture deliberately — counts, window, and 8-char hash prefixes, "never an email" — and `arch-critical.md` records "counts and hash prefixes, never identifiers" as a system-shape fact. Pick one and say it: a key id is arguably not personal data, a user UUID is pseudonymous and a departure. If the departure is intended, justify it in the spec (an eligibility violation is unactionable without the id, which is a fair argument) and amend the criteria header rather than leaving two rules that disagree.

**B8. Unprobed behaviour I am relying on the spec to flag — nit, but name them.**
The spec's assumption list covers `createApiKey`, `shouldStore`, `signJWT`, the logger and `createSession`-in-transaction. Two more are relied on silently: that `internalAdapter.createSession` leaves IP and user agent null when given no request context (asserted as a criterion, never listed as a probe), and that a `serverOnly` endpoint invoked through `auth.api` inherits the ambient transaction context at all — `signJWT` and `verifyApiKey` are both endpoints, not plain functions, so probe 4 should cover `signJWT` as well as `createSession`.

## (C) Success criteria that are untestable as written

- **The session margin has no value and no home.** "`expiresAt` ≥ the token's `exp` + the margin" appears three times; the number appears nowhere, and `limits.ts` is declared the single home of limit numbers. Unmeasurable until it is a named constant.
- **"The session write does not wait on that lock."** A non-blocking assertion has no failure mode unless it is expressed as a deadline — as written, the CI symptom is a hung suite, not a red test. State the timeout.
- **"apps/api's source gains no WhatsApp-specific code."** The scan scope is undefined, and the sibling criterion deliberately *adds* `registered_via = 'whatsapp'` to an apps/api contract test, so a naive grep fails. Per `lessons-critical.md`, the pattern needs a negative test against a known-bad line and a known-good near-miss, plus a hit count.
- **Alert thresholds** (per-key volume, 401 volume) are "over a threshold" with no number; the `limits.ts` bounds criteria likewise depend on open owner decision 3. Expected at this gate, but they are not testable until those land.
- **"No column of the row contains any substring (length ≥ 4) of the raw key."** A 68-character key yields ~65 four-character windows tested against a uuid, a base64url hash and other text columns; chance collisions give this roughly a 0.1–0.5% flake rate per run. Reformulate as: the full key absent from every column, `start` null, and the hash equal to `sha256(key)`.
- **The staging smoke sign-off** names an actor and a scope but no artifact or location, so "signed off" has no checkable state. Say where it is recorded.

By contrast, two criteria that look soft are genuinely sharp and should be kept verbatim: the logger criterion's "cannot be met by disabling the logger" (the plugin really does log the raw error at `index.mjs:~1987`, so the near-miss cases are the right test), and the production-shaped stopped-database case.

**REQUEST CHANGES** — B1 (CORS claim has no mechanism and contradicts the global `corsFor` mount), B2 (boot assertion must fail only on relation-missing, not on an unreachable database), B3 (pin the budget's executor so a refusal cannot roll the counter back), A3 (`signJWT` sets no `iat`: pass it and assert full claim-set equality with `/api/auth/token`); plus should-fixes B4–B7 and the C items.
