I'll ground this review in the actual code before flagging anything.## Review: spec 329 — service API keys and the WhatsApp token exchange

Grounded against the live tree on `develop` (spec 300 merged, `2c84795`). Files I read: `packages/auth/src/index.ts`, `schema.ts`, `reserved.ts`, `users.ts`, `limits.ts`, `apps/auth/src/app.ts`, `middleware/blocked-paths.ts`, `routes/account.ts`, `alerts.ts`, `apps/api/lib/auth/resolve-user.ts`, `system-accounts.ts`. Where I lean on library behaviour the spec does not record as probed, I say so inline.

---

### 1. WhatsApp key → non-WhatsApp user; delegation boundary

**1.1 No property check on the resolved user — blocking.** The whole delegation guarantee rests on one unstated premise: that nothing but the exchange ever writes an `auth.account` row with `provider_id='whatsapp'`. The route looks up `(provider_id='whatsapp', account_id=bsuid)` and mints for whatever `user_id` comes back, with no assertion about that user. If a `whatsapp` row ever lands on a pre-existing user — a future WhatsApp/Meta social provider configured with that `providerId` (better-auth links social accounts to an existing user; that linking behaviour is *not* recorded in your probe, so treat it as unverified), a backfill script, a cutover copy, or an operator mistake — the key mints a token for that user, and if the user is an admin that token opens `/api/account/*` and the admin surface, since `users.role` is the only admin truth. The fix is one query inside the transaction you already open: refuse unless the resolved user's address is under the non-interactive domain, `registered_via='whatsapp'`, `role` is not `admin`, and the user's *only* account row is the `whatsapp` one. Note the criteria currently pin the weaker invariant ("no `sub` of a user without a `whatsapp` account row"); the one worth pinning is "only a user whose sole account row is `whatsapp`".

**1.2 Missing service user presents as a revoked key — should-fix.** The owner check resolves the WhatsApp service user by its `service` account row on every request. The spec never says what happens when that row is absent (service user deleted, cascade from a user delete, or script not yet run): the `referenceId` comparison simply fails and the caller gets the one 401. That is a misconfiguration wearing the costume of a revoked key — the exact confusion the 500 rule exists to prevent. Make "service user not resolvable" a 500 plus an alert, and assert exactly one row (the new unique index gives you that only after migration `0001` is applied).

**1.3 Key-creation path and hashing unspecified — should-fix.** The spec says keys are issued by operator scripts but never says *how*: direct row insert (which must reproduce the plugin's hash exactly, including any server-side salt the probe did not record) or in-process `auth.api.createApiKey` (whose session/`referenceId`/`enableMetadata`/`permissions` requirements the probe also did not record). This matters because a key created with the wrong hash or a dropped `permissions` field fails at the exchange with the same byte-identical 401 as a revoked key — undiagnosable by design. Record the mechanism and the probe that proves it.

### 2. Oracle, enumeration, timing

**2.1 Membership-and-ban oracle under key compromise, with no signal — should-fix.** Any key holder can ask "has this BSUID talked to Ansari, and is that user banned" and get 200 / 403 / new-user. BSUID space is unenumerable, so this is a targeted-confirmation leak, not a harvest — but for a service that answers religious questions, confirming a specific person's use is a serious privacy outcome. The structural problem is that the only proposed detection (Open Question 13, an alert on user creations) is blind to exactly this: probing an *existing* BSUID writes no row. Make the mandatory signal volume-per-key on the exchange (requests, not creations), together with alerts on `USAGE_EXCEEDED` and `RATE_LIMITED`, which are otherwise invisible on both sides since everything collapses to 401. `apps/auth/src/alerts.ts` already has the Sentry pattern, so this is cheap.

**2.2 Body never echoed, and logging surface wider than `console` — should-fix.** The 400 body is constant and key-first ordering is right, so the public oracle story is clean. But the "no BSUID in any log" criterion only captures `console.*` from the exchange. Sentry breadcrumbs/HTTP integrations and any request-logging middleware are not covered, and a request body is the classic way a BSUID or a disguised phone number escapes. Add: no Sentry event from the exchange carries the request body, and no response echoes the input.

**2.3 Timing — nit.** New-BSUID (lock + two inserts) vs existing (one select) vs 401 are distinguishable by latency, but only to someone who already knows what they sent. Say so in the spec so the plan does not invent constant-time padding.

### 3. Concurrency and consistency

**3.1 Session creation and JWT signing mechanism unspecified — blocking.** `auth.session.token` is `notNull().unique()` (`packages/auth/src/schema.ts:70`) and the bearer plugin accepts an *unsigned* bearer, deliberately (`packages/auth/src/index.ts:344-346`). So every session this route creates carries a 30-day full-account credential — one that can reach `DELETE /api/account`. The spec never says who generates that token, with what entropy, whether the session is written by hand or via `internalAdapter.createSession` (the pattern `apps/auth/src/routes/account.ts:192` already uses), how the JWT is then signed from it, or that the session token must never be logged or returned. For a High-tier auth spec this is the one gap I would not let through to the plan: it invents a new long-lived credential without specifying its generation or handling. Name the mechanism, and add the session token to the never-log list.

**3.2 The lock cannot be tested on pglite, and the seam test is vacuous — should-fix.** The criteria admit pglite serializes connections, then assert "concurrent requests for an existing user leave exactly one session" via "test seams". A seam in your own code proves call ordering, not mutual exclusion: delete the `FOR UPDATE` and the seam test still passes. By your own lessons ("test transactional/atomic behavior against a real DB, not mocks"; "prefer failures that are loud over checks that are quiet"), these two cases need a real Postgres, or the criterion must state what the seam does and does not prove plus a source-level assertion that the session step runs inside the locking transaction.

**3.3 Signing must happen under the lock, and the claim needs softening — should-fix.** "A token is never signed from a session that dies before the token does" is not achievable: a concurrent ban (step 5), a `DELETE /api/account`, or a near-expiry replacement can kill the session after signing. Specify that signing happens inside the same transaction/lock, restate the invariant as "the session outlives the token at signing time", and add the missing cross-spec contract item: #327 must re-exchange once on a 401 from apps/api.

**3.4 User deleted mid-exchange — should-fix.** Open Question 12 makes delete-then-recreate normal. An in-flight exchange that resolved a user id can then insert a session against a cascaded-away user → FK violation → 500. Your spec-300 lesson is literally "guard a first-use insert against a concurrent delete" (and `apps/api/lib/auth/resolve-user.ts:135-160` shows the pattern). Specify the behaviour and add the scenario.

**3.5 The new unique index is the deploy-blocking step — nit.** `unique(provider_id, account_id)` is global over `auth.account`, which today holds only `credential` rows (`schema.ts:105-110`), so duplicates are unlikely — but "unlikely" belongs in a pre-apply check in the runbook, not in a reviewer's head. Also note the constraint build takes an ACCESS EXCLUSIVE lock on a table every sign-in reads.

### 4. Availability and failure modes

**4.1 The pre-401 database check misses the most likely outage — blocking.** If `auth.apikey` is absent or shaped wrong (migration `0001` not applied, or a later bump renaming a column), the plugin catches the relation error and returns `INVALID_API_KEY`; a generic `select 1` liveness probe succeeds; the route answers 401. That is the #165 class — code shipped, migration not run — reproduced inside the new credential path, and the risk table claims it is mitigated when it is not. The check before a 401 must touch the `apikey` relation itself, a boot-time assertion should fail loudly if it is missing (precedent: the boot assertion noted in `packages/auth/src/users.ts`), and the criteria need "relation absent → 500, never 401".

**4.2 Budget exhaustion is a service-wide outage with no containment — should-fix.** The exchange is the only route outside the better-auth handler with no per-user budget; `limits.ts` and `routes/account.ts` establish the opposite convention (`ACCOUNT_ENDPOINT`, 60/min per user, via the existing `consumeWindow`). One looping conversation or a token-cache bug on one BSUID can therefore consume the entire daily budget and take every WhatsApp user down, reported as 401. Add a per-BSUID budget inside the key's outer bound. Also size the budget against instances × restarts, since spec 321's 15-minute cache is per process.

**4.3 Key deletion destroys the only trail — should-fix.** Expiry prunes the row on verify, and revoke deletes by id, so the forensic record of a key that mattered is script stdout. Prefer revoke = `enabled=false` (your probe shows disabled keys are refused and kept), record issuance/rotation/revocation somewhere durable (runbook entry or a Sentry event at creation), and either add an expiry-approaching alert or drop `expiresAt` on the production key and drive rotation from the runbook.

**4.4 Internal `/token` path interactions — nit.** If signing goes through the jwt plugin's endpoint in-process, apps/auth's perimeter hooks and `TOKEN_EXCHANGE_PER_SESSION` apply, its 429 has no mapping in your contract table, and a `rate_limit` row accrues per WhatsApp session. Specify the mapping or the bypass.

### 5. Untestable criteria and missing scenarios

**5.1 "Blocked in every case and prefix variant, as the admin paths do" is false as written — should-fix.** In `apps/auth/src/middleware/blocked-paths.ts`, only `/api/auth/admin` gets prefix treatment (lines 17, 55-58); every other `BLOCKED_AUTH_PATHS` entry is matched against the exact canonical path via `BLOCKED_EXACT`. Five hardcoded `/api-key/*` strings therefore get exact matching only, and the suffix variants in Test Scenario 10 would fall through. Worse, a hardcoded list goes stale: derive the paths from `apiKey().endpoints` exactly as `ADMIN_PATHS` derives from `admin().endpoints` (`packages/auth/src/index.ts:140-148`), add an `/api/auth/api-key` prefix rule, and assert the derived list is length 5 today — so a plugin bump that adds an endpoint fails loudly instead of quietly publishing it.

**5.2 The logger criterion can be satisfied by destroying it — should-fix.** `logger: { disabled: true }` passes every log-capture assertion. Add criteria that a non-error better-auth log still appears with its level and message, that an error argument reduces to exactly `{name, code}`, and that the test feeds a known driver-error object (and a near-miss that must survive).

**5.3 "`start` not stored" rests on an unrecorded option — should-fix.** Nothing in the probe table records a config that suppresses `start`, so as written this criterion may be unsatisfiable without the script nulling the column after create. State the mechanism, and make the test stronger than "`start` is null": assert no column of the row contains any substring of the raw key.

**5.4 Missing scenarios — should-fix.** (a) `auth.apikey` absent → 500 (4.1); (b) user deleted mid-exchange (3.4); (c) the exchange rejects a session token and a JWT presented as the bearer — i.e. no auth fallback — and is not reachable under `/api/auth/*`; (d) CORS: `corsFor(CORS_ORIGIN)` is global (`apps/auth/src/app.ts:62`), so the exchange inherits CORS; it should return no allow-origin for any origin, making browser use structurally impossible; (e) concurrent verifies with the *same* key (the probe tested sequential accounting only).

**5.5 Staging smoke is someone else's gate — nit.** It depends on #327's amendment landing; name who signs it off so it cannot block or silently pass this PR.

### 6. Standing invariants

No contradiction found, and two claims I checked out as accurate rather than assumed. The exchange sits outside the handler path exactly as the account router does (`app.ts:62-67`), so `ROUTER_RULES` all-false is genuinely preserved. And the Current State claim that a second reserved domain "passes apps/api's first use unchanged" is correct for a non-obvious reason: apps/api keeps its *own* copy of `isSystemAddress` (`apps/api/lib/auth/system-accounts.ts:12-31`) rather than importing `@ansari/auth`'s. One implementation trap follows from that (should-fix): extend `isReservedAddress` only, and do **not** widen the exported `isSystemAddress` / `SYSTEM_EMAIL_DOMAIN` — those are the system-domain invariant's name and are asserted by existing tests. Two additions to the never-log rule: the session token (3.1) and the raw key, with coverage over Sentry, not just `console`.

### 7. Scope

**7.1 Missing: a documentation criterion — should-fix.** The design leans on the runbook for the limit numbers, rotation, expiry policy and the migration-before-code order, and `docs/self-hosting.md` is listed only as "to be updated". At risk tier High, with a new operator-held credential, that belongs in the success criteria with its contents named.

**7.2 Limit numbers leave their single home — nit.** `packages/auth/src/limits.ts` declares itself "the only place [limit numbers] are written down" and tests import from it. The key's numbers would live only in a DB row and the runbook. Record them there as documented constants the create script validates against, while keeping the no-defaults rule.

**7.3 Otherwise the scope is tight — nit.** The non-interactive domain, the blocked surface and the redacted logger are all load-bearing; deferring the leaderboard (OQ4) is right. Two guardrails for the plan: do not let #314's verify route creep in, and land the global logger redaction as its own commit, since it changes every better-auth log line in apps/auth.

---

**Verdict: REQUEST CHANGES** — (1) assert properties of the resolved user before minting (sole `whatsapp` account row, non-interactive domain, `registered_via='whatsapp'`, not `admin`); (2) specify session creation, session-token generation and JWT signing, and add the session token to the never-log list; (3) make the pre-401 database check touch the `auth.apikey` relation, with a boot assertion and a "relation absent → 500" criterion.
