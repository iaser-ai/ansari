### Blocking

**B1 — The stub sender does not close the OTP surface; it opens a guessable one. (1)(5)**
`/phone-number/send-otp` creates the verification row *before* it calls `sendOTP` (`routes.mjs:156-161`, then `162-173`) and nothing deletes it when the sender throws. Every refused send therefore commits a live 6-digit code (`otpLength` 6, `expiresIn` 300s — `index.mjs:11-12`) keyed by the raw number, and each send creates a **new** row, so the guess budget is `3 × sends` rather than 3. `/phone-number/verify` is unblocked, consumes that row (`allowedAttempts` defaults to 3, `routes.mjs:503`), and on success sets `phone_number_verified` and **creates a session with a session cookie** for whoever holds the number (`routes.mjs:380-392`) — a full first-class session, not an exchange JWT, on a claimed email/social account. So "there is no sender yet" does not mean "no OTP exists"; it means an OTP exists that nobody can receive and anybody can guess. The fix is small and consistent with the owner's "enable the plugin and don't block it": keep the plugin enabled, keep the paths out of `disabledPaths`, and refuse the five routes **in a before hook** so nothing is written and nothing is guessable — which is exactly the single 4xx §5.2 already promises. Set `allowedAttempts: 1` as defence in depth.

**B2 — `request-password-reset` never reaches the stub, answers 200, and its partner mints a credential row. (1)(5)(7)**
That route uses the separate `sendPasswordResetOTP` option (`routes.mjs:433`), which the phase does not set; with it unset the route still creates a reset OTP for `<number>-request-password-reset` and returns `{status:true}` — no stub call, no Sentry count, no typed error, no 4xx. `/phone-number/reset-password` then, on a correct OTP, **creates a `credential` account row when the user has none** and sets the password (`routes.mjs:475-480`). Three consequences: the amendment's "`sendOTP` is the one stub and every refusal is one 4xx" is false for two of the five routes; a WhatsApp-only holder can be handed a credential row and a password, which is both a takeover and a silent reclassification from *supersede* to *claimable* in §5.4; and `revokeSessionsOnPasswordReset: true` kills the exchange's session while the attacker keeps the account. Same fix as B1, plus an explicit pin that `sendPasswordResetOTP` is unset **and** the route cannot execute.

**B3 — Uniqueness is per-string, not per-number, so the claim/supersede decision can simply miss the holder. (1)(4)**
The plugin stores `ctx.body.phoneNumber` verbatim (`routes.mjs:340`, `369`); `phoneNumberValidator` is unset; the exchange stores Meta's `wa_id`, which carries no `+`. `phone.ts`'s normalisation is described only as "the normalisation the exchange and the budgets share" — not as something applied to what the plugin writes. `15551234567` and `+15551234567` therefore coexist happily under `UNIQUE`, and every decision in §5.4 is an exact-match lookup that takes the "held by nobody" branch. The whole amendment — one holder, verified by construction, claim vs supersede vs conflict — rests on an index that cannot see through formats. Canonicalise the body in the before hook (`signUpGuard` already shows the `return { context: { body } }` seam) and/or set `phoneNumberValidator` to refuse non-canonical input, then test both representations of one number against each branch.

**B4 — Supersede's predicate reaches an admin before the refuse branch does. (1)**
§5.4 states supersede as "the holder has no sign-in method other than WhatsApp", with role and `service` in a *separate* later bullet; the phase restates the three branches in that order and drops even the "(a user the exchange created)" parenthetical. A WhatsApp user later promoted to admin — the spec's own seeded case, since `grant-admin.ts` refuses noreply addresses — matches supersede's predicate, so a leaked key clears an admin's number and **revokes an admin's sessions**; a WhatsApp-only `service` holder is the same shape. Worse, the refuse test as specified ("a holder that is an admin") will most naturally seed an ordinary admin *with* a credential row, which the claim branch's guard already rejects: the test passes while the dangerous case stays uncovered. Make `role = 'user' ∧ no service row` a precondition of **both** claim and supersede, evaluated first, and name the WhatsApp-only-admin and WhatsApp-only-service holders in the §5.6 matrix.

### Should-fix

**S5 — Counts-only alerts make the documented repair impossible, and the phase contradicts itself. (4)(7)** Unlink is specified "with the find-by-log-line step first", yet `whatsapp-linked` and `number-superseded` are counts-only and nothing else records who was involved. The established posture for eligibility violations is *count event plus a server log line carrying the user id*; apply it to both new kinds (the linked account's id; the superseded and new user ids), never the number or the BSUID. Without it, an operator who sees `number-superseded` cannot find the orphaned user the spec tells them to repair.

**S1 — A one-body mapping in `hooks.after` cannot control the status. (2)(7)** When an endpoint throws, dispatch sets `result.status = e.statusCode`; when an after hook replaces the response it updates `result.response` only (`dispatch.mjs:238-247`), and `toResponse` prefers `init.status` over the replacement error's own (`to-response.mjs`, `isAPIError` branch). An after-hook mapping therefore returns the canonical body under the *original* status — 400 `INVALID_OTP`, 403 `TOO_MANY_ATTEMPTS`, 401 sign-in, 500 for the stub's non-`APIError` throw — and "byte-identical" passes only if the test ignores the status line. Name the seam (before hook or Express wrapper) and compare status + headers + body.

**S2 — The known-vs-unknown criterion can pass by not running. (2)(7)** If seeding the "known" number silently fails — and today the only way to seed a verified number is the exchange, which B3 can defeat — both halves of the comparison are unknown numbers and the assertion is vacuous. Require a `SELECT` proving the seeded holder exists before comparing, and an assertion that the route is reachable rather than returning the 404 a blocked path gives.

**S3 — Claim and supersede write before the ban and budget are checked. (4)** `resolveOrCreateWhatsappUser` runs before `decideUnderLock`, so the `whatsapp` row is inserted on the holder (or the holder superseded) before `banned` is read and before `consumeWindow` spends the per-user budget. A banned claimable holder gets permanently linked and then answers 403: a write kept on a refused request, and an unlink nobody knows to perform. Check `banned` on the holder under its own lock before linking, or state and test that linking a banned holder is intended. (Related: the claim path spends the *victim's* exchange budget.)

**S4 — No lock order, and the phone UPDATE's unique violation is not the create path's. (4)** Claim and conflict touch two user rows; concurrent exchanges taking them in opposite orders deadlock, which `lock_timeout = 2s` does not prevent (deadlock detection fires first) and which surfaces as an unretried 500. State "lock by ascending user id" and extend the existing source-level assertion to cover it. Separately, `decideUnderLock`'s phone UPDATE (`whatsapp.ts:186-188`) must be preceded by a holder SELECT: a unique violation there aborts the whole transaction, and "retry once" as written is a create-path rule that cannot be applied inside an aborted transaction.

**S6 — Supersede can wedge a live BSUID into a permanent 500. (1)(7)** The superseded user keeps its `whatsapp` row with no number, so if that BSUID presents the same `wa_id` again it takes the conflict branch: 500 per message plus an alert, repairable only by a manual unlink. Open question 9 makes this reachable without a recycled number — the spec explicitly accepts that a Meta format or enrolment change (the parent form `US.ENT.<id>`) yields a new BSUID for the same person. Two BSUIDs alternating for one user supersede once, then 500 forever. Name the case beside unlink in the runbook, and consider deleting the superseded user's `whatsapp` row in the same transaction so the dormant BSUID starts clean.

**S7 — `sha256(number)` is not a privacy control. (3)** The preimage space is ~10¹⁰; the key is reversible in seconds and sits in `auth.rate_limit` in the same database as the numbers. `email-limiter.ts` already HMACs session tokens under `ctx.context.secret`, so `createHmac('sha256', secret)` costs nothing here. (The owner's "raw, no HMAC" decision concerned `account.account_id`, which must be looked up; a rate-limit key has no such constraint.)

**S8 — Two statements that are no longer true, in documents other people will trust. (3)(6)** (a) "`ROUTER_RULES` stay all `false`; there is no per-IP rule" is false in substance once the plugin is enabled: the plugin ships its own rule for `/phone-number/*` (10/60, `plugins/phone-number/index.mjs`), and `/sign-in/phone-number` falls under better-auth's built-in `startsWith("/sign-in")` special rule (3/10s, `rate-limiter/index.mjs:307-311`), both keyed by `x-real-ip`. They are harmless (no legacy-layer path matches) and in fact protective — which is why they should be documented and pinned, or a later `ROUTER_RULES` entry set to `false` will silently delete a brute-force gate. (b) The runbook's pre-apply note covers the ACCESS EXCLUSIVE lock and duplicate check for `auth.account` only; `0001` now also builds a unique index on `auth.users`, the table every sign-in reads, and needs its own duplicate check in the same quiet window.

**S9 — "Applied nowhere" is inherited, not verified. (6)** The review doc records the merge precondition as "`0001` applied to staging before the merge"; the owner asserts it hasn't run. If anyone has applied the old `0001`, regenerating in place diverges silently — the new file re-creates `auth.apikey`, so the apply fails, and the journal no longer describes the database. Make the check a step of the phase (ask the operator, or read staging for the `phone_number` column) and name the fallback (`0002` carrying the two columns) so that decision isn't made under deploy pressure. Otherwise the in-place regeneration is sound: both columns are additive, nullable-or-defaulted, and invisible to 0000-era code; the only hard failure is new code on a 0000 database, which the boot check turns into a loud refusal — as intended.

**S10 — Make "never stored unverified" an invariant rather than a pinned enumeration. (7)** `CHECK (phone_number IS NULL OR phone_number_verified)` in the regenerated `0001` holds for every path in play (exchange create/update, claim, supersede, the plugin's `verify` which sets both, and the plugin's own `user.update.before` hook that clears the flag with the number — `index.mjs:25-31`) and cannot be bypassed by a path written after the pinning test. The migration is being regenerated anyway.
