BLOCKING

T1 The stub does NOT stop the five routes; it opens a guessable surface. From the plugin source: /phone-number/send-otp creates the verification row BEFORE calling sendOTP and nothing deletes it when the sender throws, so every refused send commits a live 6-digit OTP (allowedAttempts 3 per row, a new row per send); /phone-number/verify is open, consumes it and on success sets verified and CREATES A SESSION with a cookie for whoever holds the number, on a claimed email or social account; /sign-in/phone-number creates a session without ever calling sendOTP; /phone-number/request-password-reset uses the separate sendPasswordResetOTP option (unset in the phase), still creates a reset OTP and returns 200 with no stub call; /phone-number/reset-password on a correct OTP CREATES A CREDENTIAL ROW for a user that has none and sets the password, which also turns a WhatsApp-only holder into a claimable one and revokes its sessions. Required: implement the owner's 'enable the plugin, don't block it' as: the plugin enabled, its paths NOT in disabledPaths, and a BEFORE hook on exactly those five paths that spends the per-number budget and returns the one fixed response (status, headers and body, in one constant) before any plugin handler runs, so nothing is written and nothing is guessable until a real sender exists. Pin: sendPasswordResetOTP unset AND each of the five handlers cannot execute (zero verification, session, credential, user rows after a request with a correct password and a seeded valid OTP). Set allowedAttempts 1 as defence in depth. The mapping cannot be an after hook: when a handler throws, dispatch fixes the status from the error and an after hook replaces only the body, so 'byte-identical' would pass with different status lines. Probe step 1 now covers: the row-before-sender order; verify's writes; the reset routes' behaviour; and that a before hook short-circuits all five.

T2 Supersede must detach the old identity. Clearing the number and sessions but keeping the old user's whatsapp row means the old BSUID exchanges again (with phone_number omitted) and gets a fresh token for the orphaned account and its threads; a leaked key holding the old BSUID defeats the supersede. Delete the old user's whatsapp account row in the same transaction. Consequence, welcome: the old BSUID starts clean next time (a fresh user), so my residual E (permanent conflict after a Meta reset) disappears and the supersede wedge case with it; rewrite 5.5 accordingly, and the criterion 'old user's rows otherwise untouched' excludes that row.

T3 Exact holder states, role and service first. role = 'user' AND no service row is a precondition of BOTH claim and supersede, evaluated before anything else: as written, a WhatsApp-only user later promoted to admin matches supersede's predicate, and a leaked key would clear an admin's number and revoke an admin's sessions. Define four mutually exclusive states: claimable (role user, no service row, no whatsapp row, at least one credential or social row), canonical WhatsApp-only (role user, exactly one whatsapp row, its noreply address, registered_via whatsapp, no other rows), protected (admin or any non-user role, role NULL, or a service row), corrupt-or-conflicting (anything else: zero account rows, a credential row with a null password, a whatsapp row already present on a claimable holder = already-linked, malformed address or registered_via, multiple whatsapp rows). Only the first two write; the other two refuse with nothing written, 500 + alert. The matrix names the WhatsApp-only admin, the WhatsApp-only service holder and role NULL explicitly.

T4 One canonical phone form, enforced before every read and write. The plugin stores and looks up ctx.body.phoneNumber verbatim and phoneNumberValidator is unset; wa_id carries no plus. '15551234567' and '+15551234567' would coexist under UNIQUE and every §5.4 branch would miss the holder. Define the canonical form (E.164 digits with no plus, which is wa_id's shape), canonicalise in the before hook by rewriting ctx.body.phoneNumber (signUpGuard shows the return { context: { body } } seam), set phoneNumberValidator to refuse non-canonical input, canonicalise wa_id identically in the exchange, and key the budgets on the canonical string. Tests: both representations of one number against each branch, and invalid forms refused.

SHOULD-FIX

T5 Ban before link. resolveOrCreateWhatsappUser runs before decideUnderLock, so a claim inserts the whatsapp row on a banned holder and then answers 403: a write kept on a refused request. Read banned on the holder under its own lock before linking; a banned holder -> 403, no link. State that a claim spends the holder's per-user budget.

T6 Lock order and the phone UPDATE. Claim and conflict touch two user rows; concurrent exchanges taking them in opposite orders deadlock, which lock_timeout does not prevent (deadlock detection fires first) and which surfaces as an unretried 500. Lock by ascending user id; extend the source-level assertion. In decideUnderLock, precede the phone UPDATE with a holder SELECT: a unique violation there aborts the transaction and the create-path 'retry once' cannot run inside an aborted transaction.

T7 The new alerts need the eligibility posture: a counts-only Sentry event PLUS a server log line with the user ids (the linked account; the superseded and new users), never the number or the BSUID; otherwise the runbook's find-by-log-line step cannot find anyone. T8 Unlink ordering: take the user lock first (the UPDATE clearing the columns, or an explicit FOR NO KEY UPDATE), then delete the whatsapp row and the sessions, in one transaction; deleting the row first leaves an exchange race.
