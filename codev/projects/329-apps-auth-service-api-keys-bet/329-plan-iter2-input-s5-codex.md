I reviewed the documents and the actual spec-329 worktree, including better-auth 1.7.7’s installed phone-plugin source.

1. **Blocking — The stub does not disable the five routes before side effects.** The installed plugin shows that `/sign-in/phone-number` can create a session without invoking `sendOTP`; reset-request uses the separate optional `sendPasswordResetOTP` and otherwise succeeds; reset-password can change or create credentials; verify can update a user and create a session. Mapping the eventual response to a common 4xx is therefore unsafe. While stubbed, a pre-handler guard must spend the per-number budget and then return the fixed response before any plugin handler executes. Tests must use correct passwords and valid seeded OTPs, assert identical complete responses, and prove zero session, verification, credential, password, and user mutations. This relies on installed plugin behavior not yet recorded as probed.

2. **Blocking — Supersession does not actually detach the old identity.** Clearing the old number and sessions while retaining its `whatsapp` account row means the old BSUID can immediately exchange again—especially with `phone_number` omitted—and receive a fresh token for the supposedly orphaned account and its threads. A leaked key holder retaining the old BSUID therefore defeats supersession. Supersede must remove or permanently invalidate the old WhatsApp mapping in the same transaction; the criterion that the old user’s other rows remain untouched must exclude that mapping.

3. **Blocking — Holder classification is too broad and underspecified.** “No non-WhatsApp method” is not sufficient evidence of a valid exchange-created holder: zero accounts, malformed address/`registered_via`, multiple/corrupt rows, or a credential row with a null password must not enter supersede or claim. Claim must also explicitly refuse a holder already linked to another WhatsApp BSUID rather than relying on the existing `(user_id, provider_id)` unique violation. Define and test exact mutually exclusive states: claimable, canonical WhatsApp-only, protected, and corrupt/conflicting; anything outside the first two must fail without writes.

4. **Blocking — Normalization is not connected to plugin storage and lookup.** The plan shares normalization between exchange and rate-limit hashing, but better-auth 1.7.7 uses the request string verbatim for user lookup, verification identifiers, updates, and uniqueness. Unless a validator or pre-handler rewrite enforces one canonical representation, formatting variants can bypass logical uniqueness, miss claims, and potentially evade per-number budgets. Specify one canonical form for both Meta `wa_id` and plugin requests, enforce it before all reads/writes, and test equivalent variants and invalid forms. This also relies on installed plugin behavior not yet listed as probed.

5. **Should-fix — Phone password reset bypasses the project password policy.** The plugin only enforces Better Auth’s length bounds; it does not call this project’s `checkPasswordStrength`, and it can create a credential row for an account that previously had none. That is harmless only while the routes are pre-handler-stubbed. Before a real sender is implemented, the design must add the same password-strength policy, retain session revocation, and test credential creation, existing-password replacement, and weak-password refusal. This is another installed-source behavior requiring a probe.

6. **Should-fix — The exchange intentionally exposes a protected-number oracle.** A fresh BSUID plus an absent/claimable/supersedable number returns success, while an admin, service, non-user, or conflicting holder returns 500. Thus a leaked service key can distinguish protected-account phone numbers, despite OTP responses being uniform. The amendment currently requires this difference, so either explicitly accept it in the threat model and bound/alert it, or redesign the refusal response; it should not be described as enumeration-resistant without this qualification.

7. **Should-fix — Plain SHA-256 is a reversible dictionary identifier for phone numbers.** Phone numbers have a small search space, so a stable SHA-256 key or exposed prefix can be brute-forced and correlated. Use a domain-separated HMAC with the existing Better Auth secret rather than adding an environment variable, and test that raw numbers never occur in keys, logs, alerts, or Sentry. Also test email sign-in and session responses for the intended self-only exposure, not only phone sign-in.

8. **Should-fix — The plan and existing tests still contradict the amendment.** The traceability table still says the number is “never returned”; the spec constraint still says “returned by nothing”; existing `api-key.test.ts` and `options.test.ts` pin `returned: false`; and the “Unchanged” criterion does not permit those tests to change. These cannot coexist with the plugin’s `returned: true` behavior. Update all stale criteria and explicitly replace both camelCase and snake_case sign-up tests, including no-write assertions.

9. **Should-fix — High-risk concurrency evidence can pass by not running.** The real-Postgres races are described as probes/review deliverables, but “all suites green” does not prove they ran. Make the race command fail closed in the gate or require a checked artifact tied to the current revision. Add negative controls for the model/journal and boot checks, and assert retry count, final account mappings, revoked sessions, and both callers’ outcomes—not merely “one phone holder.”

10. **Should-fix — Post-commit effects and unlink locking need precise ordering.** Emit the link/supersede alert and generic notice exactly once after the identity transaction commits, even if later budgeting or token issuance fails; the notice must contain neither number nor BSUID. For unlink, acquire the user lock by clearing/updating first, then remove the WhatsApp row and sessions in the same transaction, or add an explicit `FOR NO KEY UPDATE`; deleting the mapping before acquiring the user lock leaves an avoidable exchange race.

The regenerated `0001` approach is otherwise compatible with a 0000-era service: the additions are additive, the boolean has a default, and nullable unique phone values do not disturb old inserts. Keeping `AUTH_DEPLOYED_THROUGH = null`, journal parity, and a boot check for the generated unique constraint is appropriate given that nothing has been applied.

**REQUEST CHANGES (pre-handler stub, true supersession, exact holder states, canonical phone handling, password-reset policy, oracle documentation, HMAC keys, stale criteria/tests, enforced Postgres races, post-commit/unlink ordering).**
