## Authentication & Authorization

JWT auth over Postgres (Drizzle), in `apps/api/lib/auth/` and `apps/api/lib/db/users.ts`. Established by spec 4 (auth hardening).

**Tokens.** HS256 JWTs carrying `{ user_id, type, session_version }`. Three types: `access` (~2h), `refresh` (~90d), `reset` (~1h). Stored SHA-256-hashed in the `tokens` table. Secret + expiries come only from validated `config.auth` (Zod-checked, `min(32)` secret, positive-int expiries) — never `process.env` directly. `issueTokenPair(userId, sessionVersion, exec)` is the single generate-and-store site (login/register/refresh).

**Session version (uniform revocation).** `users.session_version` is embedded in every issued token and compared on validation (`authenticateRequest`, `validateRefreshToken`); a mismatch → 401. Password reset and logout each `bumpSessionVersion` (sql `+1`) inside their transaction, so all previously-issued tokens become stale at once. Callers capture the version at authorization time and pass it into issuance — issuance never re-reads it — so a reset racing a refresh cannot mint a currently-valid pair.

**Rotation & reuse.** Refresh rotation is transactional: re-confirm the token (`lookupRefreshToken`, inside the tx), `markTokenRotated`, then `issueTokenPair` — all on the tx `exec`. A rotated token stays valid for a 60s grace window (issue #34: concurrent refreshes both succeed); replayed after grace but before natural expiry it is detected as `reuse` (reject + log). `deleteExpiredTokens` deletes only past-natural-expiry rows (retains rotated-but-unexpired rows so reuse stays detectable); wired as a low-probability opportunistic sweep on token issuance (no cron).

**Admin & system identity.** Admin = the durable `users.is_admin` flag (`requireAdmin`), never an email match. `ADMIN_EMAILS` reserves those addresses at registration and asserts (production boot, build-phase-guarded) that each already exists as an admin. System endpoints (`v2/mcp-complete`, `v1/chat/completions`) resolve their identity via `users.system_key` (`getOrCreateSystemUser`), never email; the `@system.ansari.chat` domain is reserved at registration. Reserved-address registration returns the **same** 409 as an existing-account conflict, placed before the strength check (anti-oracle).

**Feedback IDOR.** `findMessageInOwnedThread(messageId, threadId, userId)` scopes through `messages ⋈ threads WHERE threads.user_id = caller`; nonexistent / foreign-owned / mismatched targets all return an identical 404.

**Second auth stack — Better Auth (spec 59, additive).** A separate, self-contained Better Auth stack lives in `packages/auth` (`@ansari/auth`: Better Auth config, its own Drizzle schema, node-postgres client, and a lazy zod env contract) and `apps/auth` (a standalone Express service mounting `toNodeHandler(auth)` at `/api/auth/*`). It shares the physical database (`DATABASE_URL`) with `apps/api` but only through **new** tables — `user`/`session`/`account`/`verification` (note: Better Auth's singular `user`, distinct from `apps/api`'s `users`) — and shares no Drizzle code. `@ansari/auth` exports a `createAuth(db?)` factory (no import-time singleton, so importing it opens no connection); `apps/auth` constructs the instance at its entrypoint. This is deliberately additive: it changes nothing about the JWT auth above. Whether the two stacks stay separate or consolidate is spec 60's decision; db+env were folded into `packages/auth` (rather than a separate `packages/db`) specifically so 60 can relocate or merge the whole stack as one unit.

**Deploy runbook (order matters).** `drizzle-kit generate` → review SQL (never `db:push`) → apply migration → run `scripts/grant-admin.ts <email>` for each configured admin (creates-or-promotes with a bcrypt password, revokes prior tokens) → deploy (prod boot asserts admin existence and fails fast otherwise). Inspect for a pre-registered reserved address before applying the conditional system-row backfill.

## Gemini facilitator & message history

The facilitator (`apps/api/lib/facilitator/agent.ts`) answers via a Gemini tool loop: model turn (may carry parallel `functionCall` parts) → one user-role Content holding ALL of that round's `functionResponse` parts → continuation, until a final turn with no tool calls.

**Vertex history contract.** Vertex (not the public Gemini API) validates that the turn after a `functionCall` model turn carries *exactly* as many `functionResponse` parts as the model emitted `functionCall` parts; any producer or replayer of history must keep those counts in sync or the next call 400s. Two past violations: pre-#14 code pushed one single-part Content per call, and the issue #51 repetition guard's mid-chunk `break` skipped `functionCall` parts out of `toolCalls` while `finalContent` kept them (issue #70). The guard now stops text *emission* only — part processing always completes — and `gemini-client.ts` carries a Sentry tripwire that fires if `toolCalls.length` ever diverges from the payload's `functionCall` count.

**rawPayload persistence (issue #70).** `messages.raw_payload` (nullable jsonb) stores ONLY the final model turn's Gemini Content — visible text parts plus opaque `thoughtSignature` blobs, never intermediate tool rounds, so tool args/results are not duplicated and size stays bounded. The persisted payload is built from `GeminiResponse.allParts` (the COMPLETE arrival-ordered turn) — never from `rawPayload`, whose last-chunk-wins in-request semantics (#83) hold only the final delta of a multi-chunk answer — and `thought: true` parts are filtered out (reasoning is never stored). The facilitator's `done` event hands it to the stateful SSE routes behind a consistency guard: a final turn whose payload carries any `functionCall` part persists NULL (with a Sentry error) rather than poisoning the thread — a persisted orphan call would 400 every later turn. On read-back, `convertToGeminiHistory` replays a stored payload verbatim (signatures intact; Gemini 3 validates them on replay) and falls back to text-only Contents for NULL/legacy rows. `v2/mcp-complete` (one-shot threads) and `v1/chat/completions` (stateless) don't persist payloads.

**Tool-call persistence (spec 73).** Every tool dispatch is recorded — NEVER in `content` (the mobile API contract is frozen: `formatMessageContent` returns a bare string iff `content` is one text block, and appending tool blocks would silently flip every message to an array). Records live in `messages.tool_calls` (nullable jsonb; NULL, never `[]`, when no tool ran — `toolCallsOrNull()` normalizes at every persist site) as an ordered, interleaved `ToolCallRecord[]` (`db/schema/messages.ts`): `{type:'tool_use', id, name, input}` then `{type:'tool_result', tool_use_id, content, status, duration_ms, error_class?, attempts?, http_status?, skip_trigger?, citations?}`. `content` is the full `formatToolResultForGemini` output (what the model saw, ~7 KB median); `status ∈ ok | degraded | budget_skipped | limit_refused | unknown_tool` is derived from `processToolCall`'s return-typed outcome + `ToolResult.isDegraded` (never string-matched); `duration_ms` is `null` for never-executed calls; `skip_trigger` is `'T1' | 'T2'`; `error_class`/`attempts`/`http_status` come from `ToolResult.degradation`, which the four search tools populate from the real `ToolFetchError` (so `attempts: 2` marks a retried timeout, #76). Ids are minted in the facilitator loop (Gemini supplies none) so budget-skipped and limit-refused calls — which never reach `processToolCall`'s tracker — are still recorded. The accumulated array rides on EVERY terminal facilitator event (`done` and all `error` yields) and `onMessage`. Turns that produce no assistant row (facilitator `error`, empty final, mcp-complete's 502) persist their records to the separate `tool_call_orphans` table (`thread_id`, `reason ∈ error | empty_final`, `source`, `client`, `tool_calls`) via `persistOrphanToolCalls` — a table rather than invisible `messages` rows so that invisibility to thread GET, share snapshots, history replay and message-count stats holds by construction; the helper never throws, never bumps `threads.updated_at`, and logs/Sentry-warns `{name, code}` only. On the streaming routes the orphan write runs AFTER `safeClose()` (post-close DB work inside the `ReadableStream.start` closure — fine on the Node runtime). Read paths are explicit projections: `findMessagesByThread`/`getThreadWithMessages` omit `tool_calls` (keep `raw_payload` for replay), and `createThreadSnapshot` selects only id (lookup only, never written)/role/content/createdAt. The single exception, reading `tool_calls` to derive citable sources, is confined to `lib/db/citable-documents.ts` (see below); analytics select from `messages` directly and union the orphans, e.g. `SELECT r->>'status', count(*) FROM (SELECT jsonb_array_elements(tool_calls) r FROM messages WHERE tool_calls IS NOT NULL UNION ALL SELECT jsonb_array_elements(tool_calls) FROM tool_call_orphans) t WHERE r->>'type' = 'tool_result' GROUP BY 1`. Migration is `0007_tool_calls_persistence` at journal idx 6 (PR #88 took idx 5 as `0006_*`). Because `0005_*` is missing, drizzle-kit's generated prefix lags the real sequence by one — rename each new migration by hand (the next generate emits `0008_*`; name it `0009_*`).

**Citable documents (spec 168).** The sources behind an answer are DERIVED from `tool_calls`; for threads they are not stored twice (#66's `messages.documents` column was reverted in #165). Share snapshots DO carry a copy (see below). Each `tool_result` record carries `citations: [{enabled}]`, index-aligned with `content.results`. It holds the tool's own `citations.enabled`, computed once by `citabilityOf()` (`lib/tools/types.ts`), and sits BESIDE `content`, which stays exactly the Gemini payload. The flag is necessary because a zero-result search records `status: 'ok'`, and its "No Results" entry looks structurally like a real verse; neither status nor wording can tell them apart. `formatToolResultForGemini` dropped the flag because it was a Claude-API concept Gemini never used. `lib/db/citable-documents.ts` is the only serving reader of `tool_calls`. `deriveCitableDocuments` treats the jsonb as untrusted: it shape-checks every record, keeps flagged entries in dispatch order, and dedups on `(title, context, text)` with the first occurrence kept. It fails closed per record, so legacy rows without `citations`, misaligned or malformed records yield nothing and never fail the request, and it logs `{messageId, reasons}` codes only. `source.type`/`media_type` are filled from the `DocumentBlock` literal types; widening them breaks the build at that site. `findCitableDocumentsByThread` returns `{messageId, messageIndex, documents}[]`, and the raw rows never leave it. Serving uses dedicated endpoints so thread GET and share GET stay byte-identical, pinned by fixtures in `tests/fixtures/documents-contract/`. `GET /api/v2/threads/{id}/documents` is owner-scoped and derives live. `GET /api/v2/share/{id}/documents` is public and reads documents copied into the snapshot at share creation, never `tool_calls`. Because `findShareById` selects the whole `shares.content` jsonb, share GET also detoasts those copied documents and discards them: the wire bytes are unchanged, but the read cost is not. Both return `{ messages: [{ message_index, documents }] }` (the thread one adds `message_id`). `message_index` is the position in the matching GET's `messages` array, stable because messages are append-only. Replay (`messageReadColumns`) never loads documents.

## Monorepo layout, build & deploy

The repo is a pnpm workspace of `apps/*` + `packages/*`, driven by Turborepo.

**Layout & task running.** Root tasks fan out through one cached Turborepo task graph; `pnpm dev` starts both apps. Target a single package with `pnpm api <script>` / `pnpm frontend <script>`, or by running from inside the app directory.

**Docker build context.** Both images build from the repo root, never from the app directory — the pnpm workspace needs the root lockfile and both images `COPY packages packages`. The Dockerfile invocation is always `-f apps/<app>/Dockerfile …` with `.` as the build context.

**Strict env mode.** Turborepo runs in strict env mode: a variable not declared in `turbo.json` is invisible to tasks and absent from the cache key. Adding an env var means adding it to `globalEnv`, derived by four methods — the Zod schema in `apps/api/lib/config.ts`, a static `process.env.X` grep, a dynamic `process.env[` grep followed to its call-site literals, and the documented surface (`docs/self-hosting.md`, `.env.example`) for variables consumed by dependencies. Each method catches variables the others miss.

**Shared packages in the cache hash.** A `workspace:*` dependency does not put a package's contents into a consumer's cache hash. Shared packages must also be listed in `globalDependencies`, or a warm cache replays stale results against changed shared config. **Refinement (spec 59):** this bites per-task, gated by the `^` prefix in `dependsOn`. A task with a `^`-prefixed dependency (e.g. `build`'s `^build`) *does* traverse its internal dependencies' package hashes and busts on their edits without a `globalDependencies` line; a task with only un-prefixed deps (this repo's `typecheck` → `["gen:types"]`, `lint` → none) does **not** traverse them and needs the `globalDependencies` entry. Verified per-task in both directions: `apps/auth#typecheck` needed `packages/auth/src/**` listed to bust on `@ansari/auth` edits, while `apps/auth#build` busted either way. Listing a shared package is never wrong, so the prescriptive rule stands; this explains why some tasks appear "already covered".

**Railway deployment.** Deploy configuration lives in the Railway dashboard, not in `apps/*/railway.toml` — the tomls are the reviewable git record only. Watch paths must include `packages/**`, since both images copy it.

**Health endpoint.** `/api/health` returns `service: 'ansari-backend'` — a pinned public contract (spec 3), unrelated to the `apps/api` directory name. It performs a live DB ping with a 2s cap, so a cold process can legitimately 503 on its first request.

## Prototype chat display (prototypes/ansari-expo)

**Unbacked citations are hidden at display time (issue #158).** When an answer has no source documents (no tool ran, the `/documents` request failed, or an apps/api without spec 168), the model has still written its own `[N]` markers and often a trailing `Citations:` list. An assistant message with `citations.length === 0` is therefore shown through `stripUnbackedCitations` (`lib/citations.ts`): it cuts the `Citations` heading section (plain/bold/ATX, anchored to its own line) and then removes bare `[N]`. This happens in exactly two places: `mapConversationDetail` (persisted messages) and the chat screen's `onEvent` (streaming, via `stripStreamingCitations`, which also withholds an unfinished `[1` / `**Citat` tail). The streamed display is always recomputed from a raw-text ref (`rawStreamText`), never from the cleaned `streamingText`. Stored content is never modified. The done hand-off swaps by message key (`chat-reconcile.ts`), not by text, so the persisted answer may legitimately differ from the streamed one (see below).

**Real citations come from `/documents` (issue #161, spec 168).** The detail queryFn (`loadConversationDetail`, `lib/api/decode.ts`) fetches thread GET and `GET /threads/{id}/documents` in parallel, so an answer, its markers and its pills arrive together. The documents request is FAIL-SOFT: a network/HTTP error (including a 404 from an apps/api without spec 168) or a body failing `threadDocumentsSchema` renders the thread without sources and logs status or zod path only. The thread keeps its throwing zod gate. The response of the documents request never fails a conversation (#165). `joinThreadDocuments` attaches an entry only when `message_index` (a position in the RAW array, `tool` rows included, so the join runs before `mapMessage` drops them) points at the entry's `message_id` on an assistant message. Otherwise it attaches nothing and logs `{messageId, reason}`. An assistant message with documents goes through `resolveCitations` (`lib/document-citations.ts`) in `mapMessage`. Each document becomes a `Citation` from its own fields only (Qur'an: `{ar,en}` JSON + a quran.com link from the `Quran S:A` title; hadith: `{ar,en,collection,chapter,grade,lk_id}` JSON, no link, since no hadith URL scheme is verified; tafsir/mawsuah: the plain passage, shown as Arabic when mostly Arabic script). The model's `[N]` numbering is its own and does NOT follow `documents` order, so a marker is kept ONLY when its entry in the model's `Citations:` list names exactly one document, by the strongest key the entry carries: hadith `LK id` → Qur'an `surah:ayah` → encyclopedia work + volume + page → exact normalized title. The first applicable key decides; an ambiguous or empty match is not rescued by a weaker key. Unresolved markers are removed individually. Kept markers are renumbered 1..k by first appearance, and the pills share those numbers. Uncited documents follow as pills k+1..n. The `Citations:` section is always removed. If nothing resolves, every marker is removed and all documents are listed in document order. The streaming bubble has no documents, so it stays stripped; markers and pills appear when the persisted answer lands. The khushu' sample (`SAMPLE_CITATIONS` + `SAMPLE_ANSWER_CONTENT`) is now only a fallback demo: it applies to a khushu' thread's first answer when that answer has no real documents.

**Streaming bubble chrome.** While `streamingText` is set, the synthetic answer row (`item.id === streamKey.current`) renders `AnswerMessage generating` (no Copy/Share), and the list footer shows `GeneratingMark`. Both clear in the single hand-off commit, so the foot of the thread changes layout once. The standalone mark's size is `ANSARI_MARK_EMBLEM_HEIGHT` (`constants/ansariMark.ts`), shared with the sidebar emblem.
