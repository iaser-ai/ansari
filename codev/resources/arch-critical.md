## Critical facts (consult before deciding)
- Admin authorization is `auth.users.role === 'admin'` in the AUTH database, asked of apps/auth's `GET /api/account/me` with the admin's OWN JWT on EVERY admin request (outage → 503, fail closed; a dead session → 403); NEVER an email match or a JWT claim. The role is the ONLY admin truth (no admin list anywhere in apps/auth, no boot check): it comes only from `apps/auth/scripts/grant-admin.ts`, which shows the account and grants by its id (`--confirm <id>`), warning on a recent or unverified (squattable) account.
- System accounts (`ai-skill`, `leaderboard`) are resolved by `users.system_key`, NEVER by email; `@system.ansari.chat` is reserved at registration.
- Two databases, one owner each: only apps/auth connects to the auth database; apps/api reaches auth ONLY over HTTP at its PUBLIC origin (`AUTH_URL`, read through `config.authService`), like any client: public JWKS, account endpoints bound to the user's own JWT and a live `sid`, anonymous `/v2/users` pass-through. NO shared secret, NO internal listener (owner, 2026-10-17). No query crosses them; a user's id is the same UUID in both, and the app row is created on first use.
- apps/api accepts only apps/auth's EdDSA JWT (15 min, `{sub, sid}`), verified via JWKS. Revocation = deleting sessions at apps/auth, so a minted JWT stays valid until it expires (≤15 min); never treat key rotation as revocation.
- The client IP is the single `X-Real-IP` Railway's edge stamps (never `X-Forwarded-For`); per-IP limits trust it. apps/auth sees apps/api's egress IP on every legacy call, so NO path the layer calls may carry a per-IP rule on apps/auth (`ROUTER_RULES` all `false`); those per-IP limits run in apps/api (`lib/auth-service/limits.ts`). TEMPORARY until the legacy system is replaced.
- DB schema changes: `drizzle-kit generate` → review SQL → human-applied at deploy. NEVER `db:push`. Apply with `psql -v ON_ERROR_STOP=1 --single-transaction`, naming the database. Deploy order: migration → admin bootstrap (`apps/auth/scripts/grant-admin.ts`) → deploy. A PR whose tested DB paths name a new column fails `apps/api/tests/migration/migration-schema-parity.test.ts` until it bumps `DEPLOYED_THROUGH`. The bump is a human ASSERTION that the migration will be applied before deploy, NOT proof that it was. Nothing checks the target DB yet (#176), so the #165 outage class (code shipped, migration never run) is still possible.
- Turborepo runs STRICT env mode: a var missing from `turbo.json` `globalEnv` is invisible to tasks AND absent from the cache key — a cached artifact can ship wrong values while reporting a hit. Derive additions four ways (Zod schema, static `process.env.X`, dynamic `process.env[`, documented env surface).
- A `workspace:*` dependency does NOT put a package's contents in a consumer's cache hash; shared packages must ALSO be listed in `globalDependencies`, or a warm cache replays stale results against changed shared config.
- Railway deploy config is the DASHBOARD, not `apps/*/railway.toml` — the tomls are the reviewable git record only. Watch paths must include `packages/**`, since both images copy it.
- Vertex rejects any turn after a `functionCall` model turn that lacks EXACTLY matching `functionResponse` parts; `messages.raw_payload` therefore stores only the FINAL model turn, guard-checked to carry zero functionCall parts. Tool history lives in `messages.tool_calls` (+ `tool_call_orphans` for error turns). NO API response may serialize raw tool records or `raw_payload`: the thread read helpers project `tool_calls` out, and `raw_payload` stays in `messageReadColumns` for replay only. The ONE serving reader of `tool_calls` is `lib/db/citable-documents.ts`, which returns derived `document` blocks only, served by the separate `/documents` endpoints (spec 168). Thread GET and share GET carry no documents. The mobile contract is frozen: single-text `content` must stay a bare string.
